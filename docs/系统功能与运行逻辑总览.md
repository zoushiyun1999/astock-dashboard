# A股推送系统 · 功能与运行逻辑总览

> 用途：日常规划与调整的参考底座。描述的是**当前实际运行状态**（截至 2026-09-10），不是设计意图。
> 相关文档：`AGENTS.md`（工作约束）/ `MEMORY.md`（决策记录）/ `docs/云端部署方案.md`（部署细节）/ `docs/定时任务云端化方案.md`（未实施方案）

## 0. 一句话

把两个博主（韭研公社·开盘必读、淘股吧·湖南人+行鱼）的每日内容 + 技术面选股结果，自动抓取、AI 提炼、渲染成一个手机网页看板。

> ℹ️ **2026-09-12 现状**：已从删除隔离区完整恢复，**当前运行在本地模式**（提交到本地 git，无 `.gh-token` 时云端推送自动跳过）。**微信通知功能已整体下线**，本项目不再需要任何推送凭据。

**本质是一个「抓取 → 结构化 → 静态站点 → 推送」的管道，没有后端、没有数据库、没有框架。** 数据以 JS 全局变量形式存在文件里。

## 1. 全景数据流

```
【数据源】4 个博主/平台
   │
   │  ① 抓取（WebFetch / 下载图片 / AI 读图）
   ▼
【提炼】定时任务里的大模型把原文压成结构化 JSON
   │
   │  ② 写入 dashboard/data.js（window.REPORTS）
   │     dashboard/screener.js（window.SCREENER，独立隔离）
   ▼
【发布】bash tools/publish.sh "说明"
   ├─ bump_version.sh  刷新缓存版本号 v=时间戳
   │   ├─ sort_reports.js      校正 reports 顺序（旧→新，最新在末尾）
   │   ├─ optimize_calendar.py 压缩新下载的日历原图（缺 Pillow 时自动跳过）
   │   ├─ clean_calendar.js    回收日历孤儿图（防 dashboard/calendar/ 无限膨胀）
   │   ├─ sync_holidays.js     config/trade_holidays.json → dashboard/holidays.js
   │   └─ export_json.js       data.js → data.json + version.json
   ├─ git commit
   ├─ .git/hooks/post-commit → tools/gh_push_api.js（走 GitHub API，绕开不通的 git 协议）
   │     └─ 无 .gh-token 时：静默跳过、退出码 0 → publish.sh 也降级为"仅本地提交"
   └─ 有 .gh-token 时 → GitHub Actions publish.yml → https://asx.79zl.cn/（约 1 分钟）
   │
   ▼
【消费】手机浏览器打开看板 → 每 60 秒轮询 version.json → key 变了提示更新
```

**关键设计：本地只负责"生成+提交"，云端只负责"部署"。** 生成依赖大模型和国内站点抓取，放在本地定时任务；部署是纯静态文件搬运，交给 GitHub Pages。

## 2. 网页看板：5 个 Tab

站点根目录就是 `dashboard/`，整体发布。**不是单页应用，是 5 个独立的 `<section>`，靠 `switchTab()` 切换显隐。**

| # | Tab | 中文 | 数据来源 | 更新节奏 | 渲染函数 |
|---|---|---|---|---|---|
| 1 | `morning` | 早报 | `reports[].morning` | 每天 08:30 | `renderMorning()` |
| 2 | `evening` | 晚报 | `reports[].evening` | 每天 21:00 | `renderEvening()` |
| 3 | `watchlist` | 短线 | 早报`今日关注` + 晚报`明日关注` | 跟随上两者 | `renderWatchlist()` |
| 4 | `screener` | 量价 | `window.SCREENER`（独立文件） | 工作日 14:30 | `renderScreener()` |
| 5 | `calendar` | 日历 | `REPORTS.calendar` | 跟随博主发帖 | `renderCalendar()` |

### 2.1 早报（`morning`）

内容来源：韭研公社「开盘必读」文章页（正文可抓，非图片）。

```
morning = {
  title, source, sourceUrl, generatedAt,
  sections: {
    要闻简讯   : string[]   // 5-12 条，政策/产业要闻
    盘前人气股 : object     // { 韭研公社: "A、B、C", 同花顺: "...", 东方财富: "...", 淘股吧: "..." }
    重点公告   : string[]   // 10 条左右，公司公告摘要
    今日新股   : string     // 一句话，常为"今日无新股"
  },
  今日关注: [ { name, code, sector, status, reason } ]   // 8 只左右
}
```

- `盘前人气股` 是**四平台横向对比**，是看板上辨识度最高的板块之一。
- `今日关注[].status` 是自由文本，前端用正则映射成三色徽标：含「高位/风险/断板/退潮/兑现」→ 红；含「低位/补涨/未启动/安全」→ 绿；含「待确认/观察/回踩」→ 灰。见 `stBadge()`。

### 2.2 晚报（`evening`）

内容来源：淘股吧「湖南人」博客（**正文是图片**，需逐张下载 + AI 读图）+ 「行鱼复盘」文字帖。

```
evening = {
  sources: [{name, url}],           // 两个来源
  generatedAt,
  博主观点: [{ 博主, 观点 }],        // 2 条
  大盘概况: { summary, metrics: [{k, v, d, up}] },   // 上证/成交额/涨跌家数/涨停/跌停/炸板率
  连板梯队: string[],                 // "5板：百大集团（大消费/商业零售，最高标）"
  板块热点: [ { sector, stage, why, chain, picks:[{name,code,role,status,reason}] } ],
  市场情绪: string,
  links: { 湖南人, 行鱼复盘 }
}
```

- `板块热点` 是晚报的核心资产：每个主线板块带「为什么热」+「博主思路」+「个股及状态」。
- **晚报正文里不含投资日历**（2026-08-31 明确要求）。日历只走 `calendar` 专版。

### 2.3 短线（`watchlist`）—— 聚合视图，无独立数据

把早报的 `今日关注` 和晚报的 `板块热点[].picks` 拼在一起，再加上一个**近 7 日重复推荐榜**（`renderHotRepeat()`，统计被推荐 ≥2 次的个股，体现题材持续性）。

> ⚠️ **易错点**：这个 Tab 的数据源叫 `evening.明日关注`（即 `板块热点`），**不是** `watchlist` 字段。`watchlist` 只在 8/31 有历史遗留数据，现在没人写。

### 2.4 量价（`screener`）

- 数据走**独立文件** `dashboard/screener.js`（`window.SCREENER`），与 `data.js` 隔离，防止互相覆盖。
- 结构是**数组，最新在前**：`[{ date, runAt, count, criteria, list }]`，保留最近若干期，前端可切换历史期回看。
- 前端 `screenerList()` 兼容新旧两种结构（数组或单对象），不要按 `screener.date` 直接读。
- 表格列：序号/名称/板块/涨幅/换手/市值/量比/连阳/均线上。换手≥10% 和量比≥2 高亮。
- 数据来源 `tools/screener.js`：全市场约 3500 只 → 基础条件命中 50 余只 → 加连阳过滤 → 最终 5-10 只。

> `.workbuddy/memory` 里有详细筛选条件：涨幅/换手/市值/量比/K线连阳/均线上/排除项，见 `criteria` 字段实值。

### 2.5 日历（`calendar`）

- 数据在 `data.js` **顶层**（不在 `reports` 里），保留最近 5 篇。
- 展示「A股投资日历」博主（昵称"绝不追高的老韭菜"）的**月度日历原图** + 事件列表。
- 原图存 `dashboard/calendar/{文章id}_img{n}.{ext}`。
- **取舍原则：宁缺勿滥**。博主文章里的图片常常只是封面/装饰（曾抓到一张 2.2MB 的牡丹花图），下载后必须肉眼校验是否真含日历内容，否则 `images=[]` 并删本地文件。

### 3.1 本机（WorkBuddy）执行的 6 个（全部 ACTIVE）

| 状态 | 任务 | 时间 | 作用 |
|---|---|---|---|
| ACTIVE | A股早报-开盘必读资讯 | 每天 08:30 | 生成 morning |
| ACTIVE | A股早报补跑看门狗 | 每天 10:00 | **只在缺失时**补跑早报 |
| ACTIVE | A股量价选股 | 周一~周五 15:10 | 跑 `tools/screener.js` 生成 screener |
| ACTIVE | A股晚报-AI读图复盘 | 每天 21:00 | 生成 evening + 更新 calendar |
| ACTIVE | A股次日验证 | 周一~周五 21:30 | 给推荐股补实际涨跌标记 |
| ACTIVE | A股晚报补跑看门狗 | 每天 22:30 | **只在缺失时**补跑晚报（2026-09-12 由 PAUSED 改为 ACTIVE） |

> 另有一个与本项目无关的 automation「生成昨日 AI 重点资讯总结」（PAUSED，无调度规则），可忽略。
>
> **量价选股原为 14:30，2026-09-12 后移到 15:10**：14:30 仍在盘中，涨幅/换手/量比都是未定值，
> 入选数会被系统性压低（已知缺陷）。15:10 收盘后跑，数据才是终值。

**看门狗为什么存在**：08:30 抓取时会遇到「最新帖还是昨天的」——不一定是真没发，可能是页面刷新滞后或 WebFetch 的 15 分钟缓存命中。所以规则是：**先复抓一次**（带 `?t=时间戳` 破缓存）再判定"未发布"。9/9 就因此误判过一次。

**次日验证的作用**：给早报/晚报推荐的个股补 `verify: { hit, gain }` 字段，前端显示 ✅+X% / ❌-X%。**注意 `gain` 是「验证日收盘涨跌幅（相对昨收）」，不是实盘收益**——推荐股平均高开 3.78%，按开盘买入实际是亏的。这是已知的语义坑，待改。

### 3.2 云端（GitHub Actions）的 5 个 workflow

| 文件 | 触发 | 职责 |
|---|---|---|
| `publish.yml` | push 到 `dashboard/**` 或 `config/site.json`，或手动 | **发布看板**：导出 data.json → 上传 Pages 产物 → 部署 → 发布后自检 |
| `health.yml` | 每天 UTC 20:00（北京 04:00） | **健康检查**：主站/备用站可达性、是否空白页、数据新鲜度、仓库内有无硬编码死链 |

## 4. 数据结构（`dashboard/data.js`）

```
window.REPORTS = {
  updatedAt : "2026-09-10 14:30",     // 全局更新时间，页脚显示
  calendar  : [ {id, title, author, publishedAt, url, images[], events[]} ],   // 顶层，最近 5 篇
  reports   : [ {date, morning?, evening?} ],   // ⚠️ 旧→新，最新在**末尾**
  screener  : [ ... ]                  // 历史遗留镜像，实际前端读 screener.js
}
```

**三条铁律（违反会静默出错）：**

1. `reports` 顺序是 **newest-at-bottom**。前端 `idx = list.length - 1` 表示"最新一期"，顺序错了就显示错日期。
2. 裁剪必须 **先 `sort by date` 再 `slice(-7)`**。先 push 再 `slice(0,7)` 会把最新一条切掉。
3. `data.js` / `screener.js` 改完**必须**跑 `export_json.js`（或直接跑 `bump_version.sh`，它串了这个步骤），否则前端轮询拿不到新版本。

当前 `reports` 有 7 条：09-01 / 09-02 / 09-03 / 09-04 / 09-07 / 09-09 / 09-10。
缺 09-05、09-06（周末）、09-08（**PC 关机导致整天数据缺失**，是已知的可靠性问题）。

## 5. 前端运行逻辑（`dashboard/js/app.js`）

### 5.1 三层防缓存机制

手机上最容易出问题的就是"数据更新了但看不到"，所以有三层：

1. **资源版本号**：`index.html` 里所有 `<script>/<link>` 都带 `?v=时间戳`，每次发布由 `bump_version.sh` 刷新。
2. **HTML 自检重载**：页面加载 1 秒后，抓一次服务端最新的 `index.html`，比对版本号；不一致就 `sessionStorage` 记标记 + 重载一次（同一版本每会话只刷一次）。
3. **数据轮询**：每 60 秒抓 `version.json`（约 200B），`key` 变了才拉全量 `data.json`（约 133KB），底部弹出「📡 有新数据 · 点击更新」。

> `file://` 直接双击打开时，fetch 会被 CORS 拦，轮询自动跳过（数据仍由 `data.js` 静态引入）。**所以本地预览要用 `python -m http.server`。**
> 页面在后台时（`document.hidden`）不轮询，回到前台立即查一次。

### 5.2 无感更新（`applyUpdate()`）

点「更新」时**不整页刷新**，而是 fetch 新的 `data.json` 就地替换 `window.REPORTS` / `window.SCREENER` 后重渲染。会保留：
- 当前 Tab
- 当前浏览的日期（如果原本停在最新一期就继续跟到最新；如果停在历史某天就留在那天）
- 滚动位置

### 5.3 状态持久化

- 当前 Tab 存 `localStorage.curTab`，**并且**在 `index.html` 里有一段内联脚本先于 `app.js` 执行，避免刷新时先闪一下"早报"再跳回来。
- 滚动位置按 Tab 分别存 `localStorage.scroll_<tab>`。

### 5.4 顶部健康条（`renderHealth()`）

给用户一个"今天数据齐不齐"的自检，**只在交易日且过了时间阈值才报警**：

| 条件 | 阈值 | 提示 |
|---|---|---|
| 今日非交易日（周末/节假日） | — | 🔵 今日休市 · 无行情更新 |
| `morning` 缺失 | ≥ 09:30 | 🌅早报缺失 |
| `evening` 缺失 | ≥ 21:30 | 🌙晚报缺失 |
| screener 最新期 ≠ 今天 | ≥ 15:00 | 🔍量价未更新 |
| 1 项 | — | 🟡 注意 |
| ≥2 项 | — | 🔴 异常 |

休市日判断读 `dashboard/holidays.js`（由 `config/trade_holidays.json` 派生）。

### 5.5 调试出口

浏览器控制台可执行 `__aStockDebug.applyUpdate()` / `__aStockDebug.showUpdateBar()` 手动触发更新，方便排查。

#### 写 data.js 的两个安全阀（2026-09-12 审计后加，别删）

`screener.js` 与 `verify.js` 都会读改写 `dashboard/data.js`。原先的读法是：

```js
let data = { updatedAt:'', calendar:[], reports:[] };
try { eval(readFileSync(DATA,'utf8').replace('window.REPORTS =','data =')); } catch (e) {}
// ...无脑 writeFileSync(DATA, ...)
```

只要 `data.js` 有任何语法问题（例如晚报 21:00 写到一半），`eval` 抛错被 `catch {}` **静默吃掉**，
`data` 就停在这个空结构上被原样写回 —— **7 天历史 + 全部日历一次性清空**。而晚报（21:00）与
次日验证（21:30）本来就紧挨着改同一个文件，触发条件相当现实。

现在两个脚本统一改用：

| 函数 | 作用 |
|---|---|
| `loadDataStrict()` | 用 `vm.runInNewContext` 解析；**失败即中止**（报错精确到 data.js 的行号），并把读取时的规模快照成数字 |
| `saveDataSafe()` | 写回前两道校验：① `reports` / `calendar` 数量骤减（低于一半）就拒绝写回 ② **乐观锁**——文件相对读取时刻被改过就中止，避免覆盖并发的另一个任务 |

中止走 `abort()` 抛错 → 顶层 `.catch()` 统一打印并设退出码 1（不用 `process.exit`，
因为 Windows 下管道输出是异步的，直接退出可能把报错截断）。

## 8. 质量机制（这套系统真正值钱的部分）

### 8.1 防幻觉

- **个股代码必须双校验**：输出 code 后用行情接口反查名称，不一致即丢弃。
  - 起因：9/7 早报把龙版传媒写成 600936（实为北投科技）；9/3 晚报出现 3 只不存在的幻觉股（晋迪股份/琼泰集团/新相网络）。
- **日历原图必须肉眼校验**：下载后必须用 Read 工具看一眼是否真含日历内容。

### 8.2 回测口径（固定，便于跨期对比）

| 项 | 口径 |
|---|---|
| 早报 | 推荐日开盘买入 |
| 晚报 | 次日开盘买入 |
| 卖出 | 区间末盘中价 |
| 成本 | 双边万五 + 印花千五 |
| **一字板** | **必须剔除**（买入日 开=高=低=收），否则高估收益 |

> 8/31-9/7 回测：含一字板 +0.22%，剔除后 **-0.22%**。**这套数据不支持"买入即盈利"预期，看板定位是盯盘/复盘工具，不是买入信号。**

### 8.3 防线上故障

- 健康检查每天 04:00 跑，异常时**以退出码 1 结束**（GitHub Actions 运行历史标红，不再推送微信）。
- `keepalive.yml` 每周空提交一次，对抗 GitHub "60 天无活动停用 cron" 规则。
- 发布后自检（`publish.yml` 内置）。
- `.gitattributes` 固定 `*.sh` 为 LF：本机 `core.autocrlf=true`，否则脚本被重写成 CRLF 后 bash 会报 `bad interpreter` 而整条链路哑火。

## 11. 硬性规则（改东西前必读）

1. **禁止硬编码访问链接**，唯一事实源是 `config/site.json`。
2. **禁止在 `dashboard/` 下放临时文件**——该目录整体发布到公网。
3. 改 `data.js` / `screener.js` 后**必须**跑 `export_json.js`（或 `bump_version.sh`）。
4. `reports` 数组是 newest-at-bottom，裁剪必须 sort 后 `slice(-7)`。
5. 个股代码必须用 `tools/check_codes.js` 反查校验。
6. 不提交凭据/密钥，MEMORY.md 只记"位置"不记"值"。
7. **禁止改回 `workbuddy_sites_deploy` 沙箱部署**——那是历史上链接失效的根因（沙箱每次部署都变、空闲会停机）。
8. **`.git/hooks/post-commit` 必须存在**，它是本地自动上云的唯一通道。
9. 改 `.github/workflows/*.yml` 后**必须做 YAML 语法校验**——`screener.yml` 曾因跨行字符串解析失败，**6 天从未成功运行而无人察觉**。
10. **前端改动先本地截图验证再部署**——用户主用手机看，不能让他当测试员。
11. **同一文件的多处编辑必须串行**，并行编辑有竞态且工具仍返回成功。
