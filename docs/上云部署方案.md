# 上云部署方案（把定时任务从本机搬到服务器）

> 2026-09-21 制定。目标：**摆脱「电脑必须一直开着」**，让早报/晚报/选股/验证在服务器上自动跑。
>
> 状态：**代码已就绪，尚未在服务器上实测**（缺 LLM API key 与 ECS 实例）。

## 1. 为什么能搬 —— 三层架构里只有一层要改

原模式的瓶颈不在「脚本」，而在**中间的分析层**由桌面端 Agent 完成（读图、提炼、定性）。

| 层 | 组件 | 上云处置 |
|---|---|---|
| 抓取层 | `fetch_jy_article.js`（韭研）、`fetch_tgb.js`（淘股吧）、东财/新浪接口 | **原样可用** |
| 分析层 | 原为 WorkBuddy Agent | **已替换**为 `lib/llm.js` + `lib/prompts.js` |
| 写入与发布层 | `merge_report.js`、`check_codes.js`、`publish.sh`、`verify.js`、`screener.js`、`health_check.js` | **原样可用** |

## 2. 新增文件

| 文件 | 作用 |
|---|---|
| `tools/lib/llm.js` | LLM 调用层（OpenAI 兼容协议，零依赖）。支持文本与视觉、超时重试、JSON 解析容错、**按魔数判断图片类型** |
| `tools/lib/prompts.js` | 所有 prompt 集中定义（早报提炼 / 晚报结构化 / 读图转录） |
| `tools/job_morning.js` | 早报：取数 → LLM 提炼 → `merge_report` → `check_codes` → `publish` |
| `tools/job_evening.js` | 晚报：抓两个博主 → 切片 → 视觉模型转录 → LLM 结构化 → 写入 → 发布 |
| `tools/fetch_tgb.js` | 淘股吧取数器（列表 / 文章 / 正文图下载，含 `_max` 404 自动回退） |
| `tools/slice_image.py` | 长图切片（Pillow）。**必需** —— 实测有 530×6157 的超长表格图 |
| `tools/cron.sh` | cron 统一入口（时区断言 + flock 并发互斥 + 环境变量加载） |
| `tools/deploy_ecs.sh` | ECS 环境初始化（幂等） |

## 3. 环境变量（写在 `~/.astock.env`，**不入库**）

```bash
umask 077
cat > ~/.astock.env <<'ENV'
LLM_API_KEY=<你的 API Key，形如 id.secret>
LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
# 文本：免费档够用（每天只调 1~2 次，偶发 429 靠重试能扛过去）
LLM_TEXT_MODEL=glm-4.7-flash
# ⚠️ 必须关掉思考模式 —— glm-4.7-flash 是思考模型，不关则 content 恒为空
LLM_THINKING=disabled
# 视觉：**必须用付费档** —— 免费档 429 到不可用（见下方实测）
LLM_VISION_MODEL=glm-4.6v-flashx
# 可选
LLM_TIMEOUT_MS=180000
LLM_MAX_RETRY=5
LLM_VERBOSE=1
PYTHON_BIN=python3
ENV
```

- **必须用支持视觉的模型**（`LLM_VISION_MODEL`）：湖南人与行鱼的正文**全是图片**，没有文字捷径。
  仅凭这一条就排除了 DeepSeek（它没有开放的视觉 API）。
- **鉴权已自动适配两种格式**：智谱的 `<id>.<secret>` 会按 HS256 签 JWT，百炼 / DeepSeek 的
  `sk-xxx` 直接作 Bearer。换平台只改 `LLM_BASE_URL` 与模型名，**不用改代码**。
- 仓库根的 `.gh-token` 单独配置（需 `Contents: RW` + `Workflows: RW`）。

### 3.1 成本实测（2026-09-21，真实跑过量）

早报一次：输入 13.9K + 输出 2.5K token（文本）。晚报一次：9~60 张切片，每张约 2K 输入 / 600 输出。

| 环节 | 模型 | 实测成本 |
|---|---|---|
| 早报（文本） | `glm-4.7-flash`（免费档） | **¥0** |
| 晚报读图（视觉） | `glm-4.6v-flashx`（0.15 / 1.5 元每百万） | 9 张切片实测 **¥0.009** |
| 晚报汇总（文本） | `glm-4.7-flash`（免费档） | **¥0** |
| **合计** | | **约 ¥0.01/天 ≈ ¥0.3/月** |

**关于免费视觉档 `glm-4.6v-flash`**：实测**不可用** —— 连续 5 次 429（「该模型当前访问量过大」），
累计等待 135 秒才成功一次，而晚报要发 10~25 次视觉请求，根本跑不动。
付费档 `glm-4.6v-flashx` 不限流，全天不到 5 分钱。**这里不值得为省钱牺牲可运行性。**

### 4.3 环境初始化

```bash
sudo bash tools/deploy_ecs.sh
```

它会：设时区为 Asia/Shanghai → 装 Node 22 与 Python+Pillow → 配 git 身份 → 装 post-commit 钩子 → 自检。
**幂等**，任何一步失败都修好重跑即可。

**国内机房的两个下载源注意事项**（脚本已内置处理，出问题时按此排查）：

- **Node 22 不走 `rpm.nodesource.com`**。该源在阿里云内地 ECS 上经常只有几十 KB/s 甚至超时，
  卡住整条部署且报错信息指向不了真因。脚本按「就近」三级回退：
  ① `dnf module install nodejs:22`（阿里云内网镜像）→ ② `mirrors.aliyun.com/nodejs-release`
  的官方 tarball → ③ nodesource 保底。三条都不通才报错。
- **Pillow 走 RPM，不走 pip**。Alibaba Cloud Linux 3 的系统 `python3` 是 **3.6**（2021 年 EOL），
  Pillow 早已没有 cp36 预编译包 → pip 会退化成「源码编译」，而该 python 连 `_ctypes` 都没有、
  也缺 zlib 头文件，**必然失败**（2026-09-21 在真实 ECS 上实测）。
  正确做法是 `dnf install -y python3-pillow`（编译好的成品，几秒钟）。
  实在不行再装 `python3.11` 并用 `PYTHON_BIN=python3.11` 指定解释器。

> `tools/slice_image.py` 只用 `Image.open / crop / resize(Image.LANCZOS) / save`，
> 其中 **`Image.LANCZOS` 从 Pillow 2.7 到 12.3 都存在**（被删的是 `Image.ANTIALIAS`），
> 所以该脚本跨 Pillow 版本兼容，**不需要为新旧版本改代码**。

> **在 ECS 上手工敲命令时注意别名**：阿里云 Linux 沿用了 RHEL 对 root 的默认别名
> `alias cp='cp -i'`（`mv` / `rm` 同理）。所以**交互式** shell 里 `cp` 覆盖已存在文件会
> 停在 `cp: overwrite '…' ?` 等你确认，看起来像卡住。脚本内不受影响（非交互 shell
> 不展开 alias）；手工命令请用 `\cp`（反斜杠绕过别名）或直接加 `-f`。

### 4.3.1 服务器上更新代码（**不能用 `git pull`**）

内地机房 `git pull` 会报 `curl 52 Empty reply from server`（github.com 的 git 协议被干扰；
但同一台机器 `git clone` 可能成功，**时通时不通**）。而 **`api.github.com` 可用**
——发布链路本来就是走它。

**正确做法：让 API 直出原始字节**（`Accept: application/vnd.github.raw`），
再用 `install` 落盘。**不要**用 base64 + Python + `cp` 那套：
- base64 解码后经 `print()` 输出会按 locale 重编码，中文可能被写成 GBK；
- `cp` 在阿里云 Linux 上被 alias 成 `cp -i`，交互式执行会停在 `overwrite?` 等确认。

```bash
cd /opt/astock
B=https://api.github.com/repos/zoushiyun1999/astock-dashboard/contents

curl -sL -H "Accept: application/vnd.github.raw" "$B/tools/publish.sh" -o /tmp/f1 && install -m 755 /tmp/f1 tools/publish.sh && echo "✔ publish.sh"
curl -sL -H "Accept: application/vnd.github.raw" "$B/tools/git-hooks/post-commit" -o /tmp/f2 && install -m 755 /tmp/f2 tools/git-hooks/post-commit && echo "✔ post-commit"
curl -sL -H "Accept: application/vnd.github.raw" "$B/tools/deploy_ecs.sh" -o /tmp/f3 && install -m 755 /tmp/f3 tools/deploy_ecs.sh && echo "✔ deploy_ecs.sh"
```

- `install -m 755` 无条件覆盖、不读别名、不受 `-i` 干扰（`mv`/`cp` 都会）。
- 仓库是公开的，**加不加 token 都行**（加了可避免匿名 60 次/小时的限流）。

**核验（必做，别用字节数判断）**：

```bash
git hash-object tools/publish.sh tools/git-hooks/post-commit tools/deploy_ecs.sh
git status --short
```

`git hash-object` 算的就是 git blob 哈希，与 GitHub API 返回的 `sha` 同一套算法——
相同才算文件真的对上。`git status --short` 应显示这三个文件为 ` M`（改了才会显示；
**什么都没显示就说明没覆盖成功**）。

实测时间线（同一台 ECS、同一域名）：

**已排除的假设**（都验证过，不要再重复试）：
1. ~~「服务器上东财完全正常」~~ —— 21:09 那 14/14 是**成功窗口**，不是常态。
2. ~~「Node fetch 与 curl 行为差异」~~ —— 21:12 失败窗口里**两者同时失败**，
   与客户端实现无关。
3. ~~「简化请求 vs 完整请求的参数差异」~~ —— 同一窗口内两者同为成功/同为失败。
4. ~~「短时限流、几分钟自动解封」~~ —— 静置 3 分钟无效，连续失败已 >12 分钟。

**待查方向**（下次用「小时级」观测尺度，不要再用分钟级探测去猜）：
- 记录**首次触发条件**（单次请求是否也失败？还是仅在密集请求后？）
- 记录**恢复所需时长**（隔 1h / 3h 各测一次）
- 若确认是长时封禁：考虑①请求间加延时（降低触发概率）②换用其他行情源

必须保留** —— 它是防止把「网络失败」写成「入选 0 只」假数据的唯一防线。

**P1 · 晚报读图有若干部位 `无法解析模型输出为 JSON`**（已跳过、未中断任务）
- 根因：单张图内容过多 → 模型输出超上限被截断。**与批次大小无关**

### 11.3 切换计划（本机 → 服务器）
