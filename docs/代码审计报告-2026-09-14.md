## 一、已修复的 Bug（5 个真实缺陷）

### 🔴 P0-1：`health_site.js` 休市日判断结构错位，节假日必误报

**位置**：`tools/health_site.js` 第 90-91 行

```js
// 修复前
const hs = JSON.parse(fs.readFileSync(...));
return (hs[String(now.getFullYear())] || []).indexOf(today) < 0;
```

**问题**：`config/trade_holidays.json` 的真实结构是 `{ note, years: { "2026": [...] } }`。
代码取的是 `hs["2026"]`（顶层），实际应为 `hs.years["2026"]`。前者恒为 `undefined`。

**后果**：所有节假日被一律判为交易日。`freshness()` 在节假日**仍会走新鲜度检查**，
导致每个休市日（中秋、国庆等 7 天连休）线上都会误报「数据已 XX 小时未更新」，
而这条告警在 GitHub Actions 里会标红 —— 真正的故障反而被淹没在假警报里。

**验证**：
```
修复前 → 2026-09-25（中秋休市）：isTradingToday=true  ❌
修复后 → 2026-09-25（中秋休市）：isTradingToday=false ✅
```

**修复**：改取 `hs.years[年]`，并加空值兜底。5 组日期断言全部通过。

### 🔴 P0-2：`verify.js` 行情只覆盖沪深主板，创业板/科创板推荐**永久漏标**

**位置**：`tools/verify.js` `fetchQuotes()` 第 148 行

```js
// 修复前
`&fs=m:0+t:6,m:1+t:2&fields=...`
```

**问题**：`m:0+t:6`（深主板）+ `m:1+t:2`（沪主板）**不含**创业板（`m:0+t:80`）与科创板（`m:1+t:23`）。
早报/晚报推荐了创业板股票时，`findQuote()` 按名称、按代码都查不到 → 返回 `null` →
主流程 `if (q) {...}` 静默跳过，**既不报错也不记录**。

**后果**：这些推荐永远拿不到 `verify` 标记，前端不显示 ✅/❌，
也不计入健康报告的胜率统计 —— **统计口径被系统性低估**，且无任何告警。

**实测受影响数据（当前 data.js 中 4 条）**：
| 日期 | 来源 | 股票 | 代码 |
|---|---|---|---|
| 2026-09-03 | 早报 | 芒果超媒 | 300413 |
| 2026-09-04 | 早报 | 皖仪科技 | 688600 |
| 2026-09-09 | 早报 | 本川智能 | 300964 |
| 2026-09-09 | 早报 | 南大环境 | 300864 |

（108 条推荐中 4 条落在覆盖范围外。）

**修复**：`fs` 补齐 `m:0+t:80` 与 `m:1+t:23`。

### 🔴 P0-3：`check_codes.js` 绕过数据安全阀，裸写 `data.js`

**位置**：`tools/check_codes.js` 第 242 行（修复前）

```js
// 修复前
fs.writeFileSync(DATA, 'window.REPORTS = ' + JSON.stringify(data, null, 2) + ';\n');
```

**问题**：项目在 2026-09-12 审计后，为 `verify.js` 与 `screener.js` 加了双重安全阀
（`loadDataStrict` 解析失败即中止 + `saveDataSafe` 规模校验与乐观锁），
但 **`check_codes.js --fix` 仍是裸 `writeFileSync`**，两个保护全都没有。

**后果**（该脚本是 4 个定时任务之一，且带 `--fix --prune`）：这个脚本跑一轮网络校验要几分钟，
期间早报（08:30）/晚报（21:00）完全可能已经改过 `data.js`；
原实现会**毫无察觉地把对方刚写入的整期数据覆盖掉**。同时缺失「规模骤减」保护 ——
一次异常的 `data` 退化就能清空历史。

**修复**：移植 `abort` / `saveDataSafe`，在 `main()` 里记录 `loadedSrc` 与规模基线，
写回前做并发检测与骤减拦截。4 组单元断言验证（并发修改、reports 骤减、calendar 骤减、正常写回）全部通过。

### 🟠 P1-4：`sort_reports.js` 用 `eval` 解析 `data.js`

**位置**：`tools/sort_reports.js` 第 14 行（修复前）

```js
// 修复前
const m = s.match(/window\.REPORTS\s*=\s*([\s\S]*);\s*$/);
const R = eval('(' + m[1] + ')');
```

**问题**：
1. `eval` 会把 `data.js` 的代码注入当前作用域，存在同名变量污染风险。
2. 用正则截取再 `eval`，若 `data.js` 被人手改出尾逗号等语法问题，错误信息指向 `sort_reports.js`
   而非 `data.js`，难以定位。
3. 解析失败会直接抛未捕获异常，**整条 `bump_version.sh` 中断**。

**修复**：改用 `vm.runInNewContext`（与 `verify.js`/`screener.js` 同源做法），
错误准确指向 `dashboard/data.js` 行号，并显式给出友好中止信息。实测幂等（重跑内容不变）。

### 🟠 P1-5：`bump_version.sh` 静默吞掉 `export_json.js` 失败

**位置**：`tools/bump_version.sh` 第 43 行（修复前）

```bash
# 修复前
"$NODE_BIN" "$WIN_DIR/tools/export_json.js" || true
```

**问题**：`bump_version.sh` 里 5 个步骤都挂了 `|| true`（原意是"可选步骤不阻塞发布"，
对日历图压缩这类软步骤合理）。但 **`export_json.js` 是发布链路的必需环节** ——
它负责由 `data.js` 派生 `data.json` / `version.json`。

**后果**：`data.js` 已更新、`data.json` 没更新时，前端轮询 `version.json`
拿到的仍是旧 key → 永远不拉新数据。而 `publish.sh` 会照常 commit + push + 提示"发布成功"。
**症状是「看着发布成功、线上停在上一期」，且没有任何报错**。

**修复**：该步骤改为显式失败即 `exit 1`，并打印明确原因。其余 4 个软步骤保持 `|| true`。

## 二、未修改但值得注意（设计取舍 / 低风险）

以下问题**经评估后判断为可接受或影响极小，未改动**，列出供决策：

### 1. `gh_push_api.js` 删除安全阀以「文件个数」代理「扫描完整性」
```js
const safeToDelete = !only && !noDelete && parentSha &&
  remoteCount > 0 && files.length >= remoteCount * 0.5;
```
用「本地文件数 ≥ 远端一半」防误删。缺点是若真的一次性删掉超过一半文件（如大重构），
删除会被跳过、需人工介入。**这是刻意的保守取舍**，符合"宁可漏删绝不误删"的仓库保护目标，保持现状。

### 2. `health_check.js` 用 `eval` 读 `data.js`（只读不写）
第 30 行 `eval(...replace('window.REPORTS =','data ='))`。该脚本**只读不写**，
即使解析失败也只是打印告警、不会破坏数据，风险远低于写入型脚本。可后续统一到 `vm`，非紧急。

### 3. `publish.sh` 锁守卫的 `tasklist` 进程检测
实测在中文 Windows 下工作正常（无匹配时 `grep -ci` 输出 `0`、`tr` 清空白后 `-eq 0` 判定成立）。
注释里记录的两个 shell 坑（`-FI` 单破折号、`grep -c` 退出码为 1）**都是对的**。
唯一残余风险：`tasklist` 输出编码随系统 locale 变化，若某台机器上进程名匹配失败会退化为"不干预"，
此时锁不会被自动清 —— 属于安全方向的失败（宁可不清），可接受。

### 4. `screener.js` 的 `isBadName` 正则 ✅ 已修复（2026-09-14 19:30）
```js
// 修复前
function isBadName(name) { return /ST|退|N\s|C\s/.test(name); }
// 修复后
function isBadName(name) { return /ST|退|^N|^C/.test(name); }
```
`N\s` / `C\s` 要求字母后跟空白，但 A 股新股名形如 `N华虹`、次新形如 `C华虹`，
**字母紧贴名字、中间无空格**，该正则实际一个都匹配不到，形同虚设（排除新股/次新的意图完全失效）。

**修复验证**：
- 146 个真实股票名（`screener` 历期入选 + 早报/晚报推荐）**新正则零误伤**，新旧命中集合均为空。
- 15 组边界断言全通过：`N华虹`/`C华虹`/`N 华虹`/`C 华虹`/`ST中孚`/`*ST海航`/`退市海润` 正确命中；
  `中国平安`/`宁德时代`/`长春高新` 等正常股不误伤。
- `screener.js --dry` 回归结果与修复前**完全一致（25 只）**，确认无回归。

> 说明：该缺陷影响本就有限（新股通常不满足「≥2 连阳」会被后置条件过滤），
> 但修正后正则语义与注释意图一致，不再留"看起来在防、实际没防"的陷阱。

## 四、后续建议

1. **AGENTS.md 补一条硬性规则**：新增/修改任何**写入型**脚本（写 `data.js` / `screener.js`）时，
   必须使用 `loadDataStrict` + `saveDataSafe`，禁止裸 `writeFileSync`。
   （规则 16 只点名了 `verify.js`/`screener.js`，正是 `check_codes.js` 被漏掉的原因。）
2. **`verify.js` 补一条"未匹配"告警**：`findQuote` 返回 `null` 时累计计数并打印，
   避免同类覆盖缺口再次静默。
3. **`bump_version.sh` 的 `|| true` 加注释分类**：明确哪些是"软步骤"、哪些是"必需步骤"，
   防止后续维护者误加。
