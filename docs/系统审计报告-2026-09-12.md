## 二、已修复（4 项，均有实测证据）

### 1. 🔴 `publish.sh` 在无 `.gh-token` 时必然 `exit 1` —— 影响 4 个定时任务

**证据（实测）**：

```
$ bash tools/publish.sh "恢复后审计：提交待定改动"
== 1/4 刷新版本号与数据产物 ==   ✅
== 2/4 本地 git 提交 ==          ✅ commit e2256c4
== 3/4 推送到 GitHub ==
✗ 缺少令牌：设置环境变量 GITHUB_TOKEN，或把令牌写入项目根 .gh-token 文件
✗ 推送失败，请检查 .gh-token 是否有效
############ publish.sh 退出码 = 1 ############
```

**根因**：`tools/gh_push_api.js` 无令牌时 `process.exit(1)`，而 `publish.sh` 第 3 步写成
`gh_push_api.js ... || { echo "推送失败"; exit 1; }`，没有区分「**没配令牌**（本地模式，应跳过）」
和「**令牌失效**（真故障，应报错）」。`post-commit` 钩子有守卫，`publish.sh` 漏了。

**实际影响**：早报 / 量价选股 / 晚报 / 次日验证 这 4 个任务，**每天最后一次命令都返回非 0**。
数据其实已提交（第 2 步成功），但任务状态判为失败 —— 日志脏、看门狗误判、真实故障被淹没。

**修复**（`tools/publish.sh`）：

```bash
TOKEN_FILE="$ROOT/.gh-token"
if [ ! -f "$TOKEN_FILE" ] && [ -z "$GITHUB_TOKEN" ]; then
  echo "（未找到 .gh-token，本地模式：跳过云端推送）"
  echo "== 4/4 完成（仅本地仓库）=="
  exit 0
fi
```

**修复后实测退出码 = 0** ✅，且令牌存在但失效时仍会正确报错。

### 2. 🟡 新增根目录 `.gitattributes`（原先不存在）

**风险**：本机 `git config core.autocrlf = true`，仓库此前**没有 `.gitattributes`**。每次提交 git 都在警告
`LF will be replaced by CRLF the next time Git touches it` —— 意思是**下一次 checkout / 重新 clone 时，
工作区的 `.sh` 会被改写成 CRLF**。而 CRLF 的 shell 脚本在 bash 下直接报
`bad interpreter: /bin/bash^M`，`publish.sh` / `bump_version.sh` / `post-commit` 会全部哑火，
且**报错信息完全看不出是换行符问题**。

历史上没炸，只是因为文件恰好没被重新 checkout 过。这是一颗定时炸弹，尤其在你换机器 clone 时引爆。

**修复**：新增 `.gitattributes`，`*.sh` 与 `tools/git-hooks/*` 强制 `eol=lf`，`*.bat` 强制 `crlf`，图片 `binary`。
已验证生效：

```
$ git check-attr eol -- tools/publish.sh tools/git-hooks/post-commit
tools/publish.sh: eol: lf
tools/git-hooks/post-commit: eol: lf
```

### 🔴 BUG-A（最严重）：`verify.js` 与 `screener.js` 会静默清空全部历史

两个脚本原先都这样读 `data.js`：

```js
let data = { updatedAt: '', calendar: [], reports: [] };
try { eval(fs.readFileSync(DATA,'utf8').replace('window.REPORTS =','data =')); } catch (e) {}
...
fs.writeFileSync(DATA, 'window.REPORTS = ' + JSON.stringify(data, null, 2) + ';\n');
```

`data.js` 一旦有任何语法问题（例如晚报 21:00 写到一半就被读到），`eval` 抛错被 `catch {}`
**静默吃掉**，`data` 就停在这个**空结构**上被原样写回 → **7 天 reports + 全部 calendar 一次性清空**。

触发条件相当现实：**晚报（21:00）与次日验证（21:30）本来就紧挨着改同一个文件**，
加上仓库是纯本地、没有远端备份。已实测确认这条路径存在（`eval` 失败 → `data` 为空 → 写回空文件）。

**修复**：两个脚本统一改用 `loadDataStrict()` + `saveDataSafe()`：

| 防线 | 内容 |
|---|---|
| 解析失败即中止 | 用 `vm.runInNewContext` 解析（报错精确到 data.js 行号），失败就 `abort()`，绝不写文件 |
| 规模骤减拦截 | `reports` / `calendar` 数量低于读取时的一半 → 拒绝写回 |
| 乐观锁 | 写回前重新读文件，与读取时刻的原文逐字节比对，不一致就中止（防并发覆盖） |

**测试**（4 个场景，全部在临时沙箱里跑，不动项目文件）：语法坏掉 → 中止且文件 md5 未变 ✅；
缺 `window.REPORTS` → 中止 ✅；reports 被清空 → 拦截 ✅；并发改动 → 拦截且未覆盖 ✅；正常 → 写回成功 ✅。

> **过程中的自查**：第一版修复本身有两个缺陷，都是测试才发现的 ——
> ① `abort()` 抛错后顶层没打印消息（运维看不到原因）；
> ② `saveDataSafe(…, loaded.data, …)` 里 `next` 与 `prevData` 是**同一个对象引用**，
> 调用方就地修改会连带改掉基线，"骤减"检查永远不触发。已改为传**数字快照**。
>
> 另外中止改用 `abort()` 抛错 + 顶层 `.catch()`，不用 `process.exit(1)` ——
> Windows 下管道输出是异步的，`process.exit` 实测会把关键报错截断。

### 🟡 BUG-B：量价选股改到 15:10，但前端阈值没跟着改

`dashboard/js/app.js` 的健康条里有：

```js
{ name: '量价选股', time: … : '14:30', state: st(scToday, 870) }   // 870 分 = 14:30
```

`st(done, dueMin)` 的语义是「过了这个点还没有数据就标 miss」。任务在 2026-09-12 已后移到 **15:10**，
阈值却还是 14:30 → **每个工作日 14:30~15:10 看板都会误报「量价选股缺失」**，页脚也一直显示
「量价选股 14:30」。这是我从渲染截图里发现的（不是从代码里）。

**修复**：显示值改为 `15:10`，阈值改为 920（15:20）。顺带把另两个阈值也加上运行余量，
避免任务刚开始跑的那几分钟天天误报：

| 项 | 任务开始 | 原阈值 | 新阈值 |
|---|---|---|---|
| 早报 | 08:30 | 8:30（510） | 8:40（520） |
| 晚报 | 21:00 | 21:00（1260） | 21:10（1270） |
| 量价选股 | 15:10 | 14:30（870）❌ | 15:20（920） |

改完按硬性规则 7 重新截图验证：页脚已显示「量价选股 15:10」✅。

### 🟡 BUG-C：`evening` 两套结构描述同一批内容，且会互相矛盾 → 前端两个 Tab 数字对不上

`evening` 里有 `板块热点`（晚报 Tab 用，扁平摘要）与 `明日关注`（短线 Tab 用，带 picks 明细）——
**服务不同视图，所以两个都要保留**，但它们描述的是同一批板块。问题在于：

- 任务提示词写的是「明日关注（**即** evening.板块热点）」→ **暗示两者是同一个东西，其实结构完全不同**，
  执行时只能各写一遍，于是产生漂移
- 实测 09-03：`板块热点` **10** 条 vs `明日关注` **8** 条 —— 用户同一天在两个 Tab 看到不同的板块数。
  查 `logs/2026-09-03.md`：日志记载「明日关注：8 个板块」，而 板块热点 把
  「黄金白银/小金属」与「航运/海运」合并成了「黄金白银/航运」，还多出一个「粮食/种业」
- `health_check.js` 原先**只校验 `明日关注`，完全不校验 `板块热点`** —— 后者可以整个缺失而无人察觉

**修复**：
1. 任务 3（晚报）的 prompt 把两者拆成两个显式步骤，明确「同一批板块的两种结构，条数必须完全一致」，
   并给出各自的字段清单与派生规则
2. `health_check.js` 新增两项检查：`板块热点` 缺失或条目缺 `name` → ERROR；
   与 `明日关注` 条数差 ≥2 → WARN（**且只对最新一期计入退出码**，历史遗留降为提示，
   否则体检会永久失败、告警失去意义）

### 🟡 GAP-D：本地模式下没有任何"管线停摆"检测

新鲜度检查只在 `tools/health_site.js` 里，而它**只被 `.github/workflows/health.yml` 调用**。
当前是本地模式、不推 GitHub → 等于**根本没有机制发现"三天没出数据"**。

**修复**：`health_check.js` 新增断更检测，关键是能区分两种完全不同的原因：

| 现象 | 判定 |
|---|---|
| 交易日无 report，但 `logs/<日期>.md` 存在 | 数据源当日没发内容，**系统行为正确**（09-08 就是这样） |
| 交易日无 report，且 `logs/<日期>.md` 也不存在 | **管线压根没跑**（PC 关机/任务失败）→ WARN |

实测输出：`ℹ️ 交易日无数据但已运行（数据源未发布，属正常）：2026-09-08` —— 无假警报 ✅
