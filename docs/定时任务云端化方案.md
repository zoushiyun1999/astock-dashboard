> 目标：让「检测博主更新 → 生成简报 → 更新看板 → 微信推送」整条链路脱离本地 PC，
> 改成云端按周期自动运行。
>
> 本文所有可行性结论均来自 **2026-09-10 在 GitHub Actions 真实环境跑通的探测实验**，
> 不是纸面推演。实测日志见文末附录。

## 三、目标架构

### 3.1 核心设计：探针与生成分离

当前系统的做法是「到点就跑全流程」。云端化后应该拆成两层：

```
┌─ 探针层（便宜、高频）───────────────────────────┐
│  每 10–15 分钟跑一次，只做一件事：               │
│  抓数据源列表页 → 提取最新文章 ID → 与上次比对    │
│  耗时约 5–10 秒，不调用大模型，不写数据          │
│  输出：changed = true / false                    │
└───────────────────┬──────────────────────────────┘
                    │ 仅当 changed = true
                    ▼
┌─ 生成层（昂贵、低频）───────────────────────────┐
│  1. 抓正文 / 下载图片                            │
│  2. 调用大模型 API（读图 + 摘要提炼）            │
│  3. 写入 data.js → 跑校验 → 导出 JSON           │
│  4. 发布到固定域名（已有 publish.sh 逻辑）       │
│  5. 微信推送                                     │
│  耗时约 2–5 分钟                                 │
└──────────────────────────────────────────────────┘
```

**为什么要分离？** 因为「检测更新」和「生成内容」的成本差两个数量级。
1 分钟级的探针一天跑 100 次也没关系；但每次探测都触发一次 AI 读图就是纯浪费。
博主不会在凌晨三点发帖 —— **检测的意义是"及时"，不是"频繁"。**

### 3.2 建议的探测时刻表（基于各源实际发布规律）

数据来自 `config/sources.json` 里已记录的发布窗口：

| 数据源 | 发布窗口 | 探测策略 | 每日探测次数 |
| --- | --- | --- | --- |
| 韭研公社·开盘必读 | 07:30–08:10 | 07:30 起每 10 分钟 | 6 |
| 淘股吧·湖南人 | 16:08–17:28 | 16:00 起每 15 分钟 | 6 |
| 淘股吧·行鱼复盘 | 20:00–20:30 | 19:45 起每 15 分钟 | 5 |
| 韭研公社·投资日历 | 不定期（月度） | 每日 18:00 一次 | 1 |
| **合计** | | | **约 18 次/天** |

相比「全天每 15 分钟盲轮询」（96 次/天），这个策略**资源消耗降到 1/5，及时性反而更好**。
公开仓库下这些全在免费额度内，但省下的时间直接体现在 LLM 调用次数上。

### 3.3 状态存储：怎么记住"上次看到的文章 ID"

推荐用**仓库内文件**（最简单、可审计、天然有历史）：

```
state/last_seen.json
{
  "jiuyan_open_read": { "id": "3y6pm9sral3", "title": "9月10日开盘必读资讯", "checkedAt": "..." },
  "tgb_hunanren":     { "id": "2uYHu0t8ztH", "title": "9.10湖南人涨停复盘...", "checkedAt": "..." },
  "tgy_xingyu":       { "id": "...", "checkedAt": "..." },
  "jiuyan_calendar":  { "id": "11cnegurk6s", "checkedAt": "..." }
}
```

探针跑完如果发现变化，就把新 ID 写回该文件并提交 —— 这样**上一次的状态就是提交历史**，
既能回溯"系统哪天抓到了什么"，也不依赖任何外部数据库。

> 替代方案：Cloudflare KV / 云数据库。**对个人项目属于过度设计**，不推荐。

## 四、三种技术路线对比

### 方案 A：GitHub Actions（推荐）

| 维度 | 评价 |
| --- | --- |
| 可行性 | ✅ 已实测 |
| 月成本 | **¥3–10**（公开仓库计算免费，只有 LLM 费用） |
| 改动量 | 中（需把生成逻辑从 agent 移植为脚本） |
| 定时精度 | ⚠️ 弱。cron 可能延迟 15–30 分钟，高峰期更久 |
| 稳定性 | 高。GitHub 基础设施，无休眠问题 |
| 备案要求 | 无（走 GitHub 域名） |
| 复用现状 | 最大 —— publish.yml / health.yml 已在跑 |

**适用**：当前场景。日常简报对"分钟级准时"没有硬要求，
早报晚 15 分钟、晚报晚 30 分钟都可接受。

### 方案 B：Cloudflare Workers + Cron Triggers

| 维度 | 评价 |
| --- | --- |
| 月成本 | 免费版 ¥0，但**有硬限制**；付费版 $5/月（≈¥36） |
| 定时精度 | 免费版 Cron **最快每小时一次**（且账号内限 5 个） |
| 致命限制 | **免费版单次调用 CPU 时间仅 10ms** —— 抓取+解析+调 AI 完全不够 |
| 改动量 | 大（要重写成 Worker 运行时，不能用 Node 的文件系统、child_process） |

**结论：不推荐。** 10ms CPU 限制决定了它跑不了这个任务；
升到付费版（$5/月 + 每小时触发）反而比方案 A 更贵且更不灵活。
它的强项是"高并发边缘 API"，不是"定时批处理"。

### 方案 C：国内云函数（腾讯云 SCF / 阿里云函数计算 FC）

| 维度 | 评价 |
| --- | --- |
| 月成本 | 基本 ¥0（SCF 免费额度 100 万次调用 + 40 万 GB·s/月，实际用量占不到 1%） |
| 定时精度 | ✅ **好**。支持秒级 Cron，比 GitHub 准时得多 |
| 网络 | ✅ **最优**。国内 IP 抓国内站点延迟低、无防盗链风险 |
| 备案 | ⚠️ 只要不绑国内 CDN 域名就不需要；但实名认证是必须的 |
| 改动量 | 大（部署流程、依赖打包、日志体系全要重做） |
| 风险 | 各家 SDK 差异大，调试成本高 |

**适用**：如果你将来对**早报准点率**有硬要求（比如必须 8:30 前推送），
方案 C 是唯一能保证准时的选择。建议**先用 A 跑通，确有需要再迁**。

### 对比总表

| | A. GitHub Actions | B. Cloudflare Workers | C. 国内云函数 |
| --- | --- | --- | --- |
| 月成本 | **¥3–10** | ¥0–36 | ¥0–20 |
| 定时精度 | 差（±30min） | 差（每小时） | **优（秒级）** |
| 改动量 | 中 | 大 | 大 |
| 复用现有代码 | **高** | 低 | 中 |
| 国内源稳定性 | 好（实测通过） | 好 | **最好** |
| 推荐度 | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐（进阶） |

### 5.3 总成本结论

> **推荐方案（A + 均衡档模型）：¥6–10/月，一年约 ¥80–120。**
>
> 即使选"追求质量"档，也不超过 ¥30/月。
> 唯一可能超预期的是图片数量波动（比如某天博主发了 40 张图），
> 但按量付费不存在"爆账单"风险，顶多单日多几毛钱。

### 5.4 省钱要点（不牺牲质量的三个手段）

1. **探针与生成分离**（见 3.1）—— 最大头，直接砍掉 80% 无效调用
2. **图片降采样**：读图前把图片缩到长边 1280px，token 消耗可降 40–60%，OCR 准确率几乎无损
3. **文字任务不用 VL 模型**：行鱼复盘、开盘必读是纯文字，用便宜的文字模型（差价 5–10 倍）

## 六、注意事项（坑都在这）

### 6.1 必须知道的平台限制

| 限制 | 说明 | 应对 |
| --- | --- | --- |
| **cron 不准时** | 官方文档明确：高负载时可能延迟，**"每小时的整点"最堵**。延迟 15–30 分钟常见 | 避开整点（用 `:07`、`:23` 这类分钟数）；关键任务留足缓冲 |
| **最小 5 分钟间隔** | `*/5 * * * *` 是下限，写更密也不会生效 | 按 3.2 的窗口策略走 |
| **60 天无活动自动禁用** | Public 仓库的 schedule 会在 60 天无仓库活动后被自动停用 | ✅ 已有 `keepalive.yml` 每周空提交解决 |
| **只在默认分支运行** | workflow 文件必须在 main 分支 | 已满足 |
| **无失败通知** | GitHub 不会因为定时任务失败而通知你 | ✅ 已有 `health.yml` 每日体检 + 微信告警 |
| **job 最长 6 小时** | 单次运行上限 | 我们每次 5 分钟内，无影响 |

### 6.2 代码层面的坑

1. **东财 / 新浪必须带 Referer**（实测发现，本地不会遇到）
   ```bash
   -H 'Referer: https://quote.eastmoney.com/'    # 东财
   -H 'Referer: https://finance.sina.com.cn/'    # 新浪
   ```
   同时带浏览器 UA。缺任何一个都可能被拒。

2. **GitHub Actions 的 YAML 里别写多行 shell 字符串**
   `screener.yml` 曾因跨行 `desp="..."` 导致 YAML 解析失败，**6 天没跑成功而无人察觉**。
   改用 `printf` 或单行；改完必须做 YAML 语法校验。

3. **时区**：GitHub cron 是 UTC。北京时间 08:30 = UTC 00:30。
   建议在 workflow 里设 `env: TZ: Asia/Shanghai`，但 cron 表达式本身仍按 UTC 写。

4. **跑完别忘了提交状态文件**，否则下次探针会重复判定"有新内容"。
   注意 `git push` 在 Actions 里要用 `GITHUB_TOKEN` 并声明 `permissions: contents: write`。

5. **凭据全部走 Secrets，绝不进仓库**
   LLM API Key 存 `Secrets`，通过 `${{ secrets.XXX }}` 注入环境变量。
   注意：`.gitignore` 对 API 推送无效（我们已被 GitHub 用 422 拦过一次），
   靠的是 `gh_push_api.js` 里的 `DENY_FILE` / `DENY_CONTENT` 双重扫描。

### 6.3 质量层面的坑（**最重要，别跳过**）

**当前系统的"智能"寄生在 WorkBuddy agent 上。** 我能用 Read 工具逐张看图、
理解上下文、判断哪些内容值得写进摘要——这些能力换成 API 调用后**不会自动保留**。

云化本质上是一次**重写**，不是搬迁。具体风险：

| 环节 | 现在的做法 | 云化后 | 风险 |
| --- | --- | --- | --- |
| 读图 | agent 逐张 Read，理解版面语义 | 调 VL 模型，返回文本 | 可能丢失版式结构（表格错位） |
| 提炼博主观点 | agent 综合判断，抓"博主的思路" | 需在 prompt 里精确描述 | 容易退化成数据罗列 |
| 个股代码 | 靠 `check_codes.js` 反查兜底 | 同样可用 | 低 |
| 投资日历 | agent 看图确认"是不是真日历" | 需加启发式校验 | 中（可能收进装饰图） |

**建议的应对**：
- 先用云化版本与当前 agent 版本**并行跑 1–2 周**，人工对比输出质量
- 把当前 prompt 里的详细规则（博主观点 150-300 字、status 字段格式、代码铁律）
  **原样搬进 API 调用的 system prompt** —— 这些规则是踩坑换来的，别丢
- 保留"质量不达标就降级"的分支（如读图失败时退回标题+链接）
- **完全确认质量达标后，再停掉本地 automation**

## 七、落地步骤

### 阶段 1：探针上云（半天，风险最低）

1. 写 `tools/probe.js`：读 `config/sources.json` → 抓各源列表页 → 提取最新 ID → 对比 `state/last_seen.json`
2. 写 `.github/workflows/probe.yml`：按 3.2 的窗口时刻表触发
3. 探针只输出日志 + 提交状态文件，**不生成内容**（先观察几天，确认探测准确率）
4. 用 `workflow_dispatch` 手动触发验证

**收益**：立刻验证"云端检测更新"是否可靠，零风险。

### 阶段 2：纯文字生成上云（1 天）

1. 写 `tools/generate_text.js`：处理早报（开盘必读）与行鱼复盘（都是纯文字）
2. 接 DeepSeek V4 Flash，prompt 从现有 automation prompt 移植
3. 复用已有的 `publish.sh` + `notify_digest.js` 发布链路
4. **与本地 agent 版本并行**，对比 3–5 天

**收益**：早报完全脱离 PC，且成本极低（文字模型便宜）。

### 阶段 3：读图生成上云（2–3 天，工作量最大）

1. 写 `tools/generate_vision.js`：下载图片 → 调 Qwen3-VL → 结构化输出
2. 处理湖南人复盘、投资日历两个读图场景
3. 加图片降采样（长边 1280px）控成本
4. 加投资日历的"是否真日历"启发式校验（避免收进装饰图）
5. **并行跑 1–2 周**，人工比对质量

**收益**：晚报脱离 PC。到此为止整个系统 7×24 无人值守。

### 阶段 4：收敛（可选）

- 确认云端版本稳定后，暂停本地 automation
- 保留本地脚本作为**手工补跑通道**（遇到云端抓取异常时可以立即补救）

## 八、需要你拍板的三件事

### 决策 1：仓库保持 Public 吗？

- **保持 Public**：Actions 无限免费，成本最低。但 workflow 文件、抓取逻辑对所有人可见
  （**不含任何密钥**，密钥在 Secrets 里）
- **改 Private**：逻辑不外露，但 2000 分钟/月额度，高频探测会超支

我的建议：**保持 Public**。这个系统的价值在"数据整合"而非"代码保密"，
且看板本身就是公开的。真要保护策略细节，可以把核心逻辑抽到 Private 仓库由 Public 仓库调用。

### 决策 2：先做哪一阶段？

我的建议：**阶段 1 立即做，阶段 2 紧接着，阶段 3 看你耐心**。
阶段 1+2 就能让早报完全无人值守，投入产出比最高；
阶段 3 是硬骨头（读图质量需要反复调试）。

### 决策 3：LLM 供应商选谁？

- **阿里百炼（通义千问 VL）**：中文 OCR 强、价格低、实测连通 —— **推荐首选**
- 智谱 / 豆包：备选，可用于对比质量
- 海外模型（GPT-4o / Gemini）：价格高 5–10 倍，且国内访问不稳定，不建议
