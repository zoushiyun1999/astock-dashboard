## 1. 一分钟看懂

页面本身**没有任何后端**。它是一个纯静态站点：数据在构建时（定时任务运行时）写进 `.js` 文件，
浏览器加载这些文件后由 `app.js` 渲染。所以「页面出问题」只有两种可能：
**① 数据文件没被写好 ② 渲染逻辑读错了字段**。

```
【本地定时任务，每天跑】
  抓取源站 → AI 提炼 → 写入 dashboard/data.js  ← 唯一的"数据写入"动作
                                    │
                         bash tools/publish.sh
                                    │
                    ┌───────────────┴────────────────┐
                    │  bump_version.sh 派生产物：      │
                    │   data.json      （前端轮询用）   │
                    │   version.json   （几百字节指纹） │
                    │   holidays.js    （休市日）       │
                    │   index.html 的 ?v= 版本号       │
                    └───────────────┬────────────────┘
                                    │
                             git commit → post-commit 钩子
                                    │
                    ┌───────────────┴───────────────┐
                    │ 有 .gh-token：推送 GitHub      │
                    │  → Actions → https://asx.79zl.cn/ │
                    │ 无 .gh-token：仅落本地仓库      │
                    └───────────────────────────────┘

【手机浏览器】
  index.html  ── 加载 4 个脚本（data.js / screener.js / holidays.js / app.js）
      │
      └─ app.js 读 window.REPORTS 渲染 5 个 Tab
            每 60 秒轮询 version.json（几百字节）
              指纹变了 → 拉 data.json（119KB）→ 就地替换 + 重渲染（不整页刷新）
```

## 2. 页面加载与运行逻辑

### 2.1 加载顺序（`index.html`）

| 顺序 | 内容 | 作用 |
|---|---|---|
| 1 | `<head>` 里的 no-cache meta + `?v=202609122153` | 见 2.2 防缓存 |
| 2 | 内联脚本（第 62-78 行） | **先**把上次浏览的 Tab 恢复出来，避免"闪回早报再跳走" |
| 3 | `<script src="data.js">` | `window.REPORTS` ← 全部主数据 |
| 4 | `<script src="screener.js">` | `window.SCREENER` ← 量价选股历史（独立文件，防被主数据覆写） |
| 5 | `<script src="holidays.js">` | `window.TRADE_HOLIDAYS` ← 休市日，只用于前端显示「休市」 |
| 6 | `<script src="js/app.js">` | 渲染逻辑 + 交互 + 轮询 |

> ⚠️ 关键点：**首屏渲染只用 `data.js`，不用 `data.json`**。`data.json` 只服务于"运行中热更新"。

### 2.2 三层防缓存（这是这套东西最值钱的工程细节）

手机浏览器缓存很顽固，静态托管又没有 `Cache-Control` 可配，所以用了三层：

| 层 | 机制 | 位置 |
|---|---|---|
| 1 | 每个资源引用都带 `?v=时间戳`（`bump_version.sh` 每次发布时刷新 5 处） | `index.html` |
| 2 | 页面加载 1 秒后 fetch 自己的 HTML，比对里面的 `?v=` 与当前的是否一致，不一致就 `location.replace` 自动重载一次（同版本每会话只刷一次） | `index.html` 第 98-119 行 |
| 3 | 轮询 `version.json`（`key` 是 data.json 内容的 md5 前 16 位），变了才拉全量 | `app.js` 第 574-599 行 |

### 2.3 `app.js` 的模块状态（第 12-16 行）

```js
var list = window.REPORTS.reports.slice().sort(按 date 升序)  // 最新在末尾
var idx  = list.length - 1        // 当前展示第几天
var curTab = 'morning'            // 当前 Tab
var calIdx = 0                    // 日历 Tab 展示第几篇（0=最新）
var scIdx  = 0                    // 量价 Tab 展示第几期（0=最新）
```

`list` 特意又排了一次序 —— 因为前端 `idx = length-1` 依赖"最新在末尾"，不能假设数据写入方一定排好。

### 2.4 `render()` 做了什么（第 482-522 行）

**一次调用会重建全部 5 个 Tab 的 DOM**，顺序：

1. header：日期、星期、`最新一期 / 历史 · 日期`
2. header 右上状态区（`srcMeta`）：4 个数据源各自的「时间 + 状态」（已生成/待更新/未更新/休市）
3. **5 个 section 的 `innerHTML` 全量重写**（早报/晚报/短线/日历/量价，含隐藏的那些）
4. footer：各源最新更新时间
5. `renderHealth()`：顶部数据健康条
6. `updateDateNav()` / `positionGlider()` / `updateEveningDot()`

### 2.5 交互入口

| 交互 | 函数 | 行为 |
|---|---|---|
| 切换 Tab | `window.switchTab(tab)` | 只切 `.hide` class + 滑动下划线，**不重渲染** |
| 翻日期 | `window.step(±1)` | 改 `idx` → 调 `render()`；早报/晚报/短线可用，量价/日历下会隐藏日期条 |
| 切换日历篇 | `window.showCal(i)` | 改 `calIdx`，只重渲染 `sec-calendar` |
| 切换选股期数 | `window.showSc(i)` | 改 `scIdx`，只重渲染 `sec-screener` |
| 手动更新 | `__aStockDebug.applyUpdate()` | 控制台调试出口 |
| 持久化 | `localStorage` | `curTab` / `lastSeenEvening`（晚报红点）/ `scroll_<tab>`（滚动位置） |

### 2.6 热更新（第 601-643 行）

```js
轮询 version.json（每 60 秒，页面隐藏时不轮询，回到前台立刻查一次）
  指纹变了 → 底部弹出「📡 有新数据 · 点击更新」
  用户点击 → fetch data.json → 替换 window.REPORTS / window.SCREENER
           → 重新 list/idx（若原本停在最新一期则继续跟到最新，否则保持看的那个日期）
           → render()
```

**这是"无感更新"**：不整页刷新，所以正在看的 Tab 和日期都不会丢。

> `file://` 直接双击打开时 `fetch` 会被 CORS 拦，第 577 行会跳过轮询 —— 此时页面只用首屏加载的 `data.js`，功能仍然正常，只是不会自动更新。

### 3.2 逐 Tab 渲染逻辑

| Tab | 渲染函数 | 依赖字段 | 空数据时 |
|---|---|---|---|
| 早报 | `renderMorning(r)` | `r.morning` | 「早报待更新 / 每天 8:30 自动生成」 |
| 晚报 | `renderEvening(r)` | `r.evening` | 「晚报待更新 / 每天 21:00 自动生成」 |
| 短线 | `renderWatchlist(r)` | `r.morning.今日关注` + `r.evening.明日关注` + 全部 `list`（算重复推荐） | 「短线关注待更新」 |
| 量价 | `renderScreener()` | `window.SCREENER`（**与日期无关，自带期数切换**） | 「量价选股待更新」 |
| 日历 | `renderCalendar()` | `window.REPORTS.calendar`（**与日期无关，自带篇数切换**） | 「投资日历待更新」 |

> ⚠️ **量价与日历不跟随日期条**。它们是独立的时间轴（`scIdx` / `calIdx`），
> 所以在这两个 Tab 下日期切换条会被隐藏（`updateDateNav()` 第 437-440 行）。

### 3.3 顶部状态区与健康条

两者共用**同一个到期时间常量** `DUE`（`app.js` 第 18-24 行）：

| 数据源 | 任务开始 | 到期点 `DUE` |
|---|---|---|
| 早报 | 08:30 | `morning: 520`（8:40） |
| 晚报 | 21:00 | `evening: 1270`（21:10） |
| 量价选股 | 15:10 | `screener: 920`（15:20） |

**到期点 = 任务开始时间 + 约 10 分钟运行余量**。不能直接写任务开始时间，
否则任务刚开始跑的那几分钟会天天误报「未更新」。

| 位置 | 函数 | 判定 |
|---|---|---|
| header 右上 + footer | `srcMeta()` | 按 `DUE` 给出每源的 `state`（已生成/待更新/未更新/休市），并标 `planned` 区分"计划时间" |
| 顶部健康条 | `renderHealth()` | 先判「最新一期是不是今天」，再按 `DUE` 逐项报缺失 |

> ⚠️ 改任务时间时**只需改 `DUE` 一处**。2026-09-12 之前这两处各写一套数字，
> 结果量价任务后移到 15:10 时只改了一处，健康条每天 15:00 起误报。
> 另外改完请跑 `node tools/_test_health_logic.js`（17 项断言）。

### ⚪ 6.4 换日期时会重建全部 5 个 Tab 的 DOM（含 41 兆像素的日历长图）

`render()` 无条件重写 5 个 section 的 `innerHTML`（第 508-512 行）。
在早报 Tab 上点「前一天」，虽然日历 Tab 是隐藏的，它的 4 个 `<img>` 仍会被销毁重建 ——
其中两张是 2008×20640 / 2008×23960 的长图。

**建议**：只重渲染当前 `curTab` 对应的 section，其余标记为"脏"、切过去时再渲染。
（顺带能做的一件：给 `cal-img` 加 `loading="lazy"`，但要注意补一个占位高度，否则会造成布局跳动）

### 🟡 6.5 日历长图的解码成本

单张 2008×20640 = **41.4 兆像素**，手机上解码约 166MB 位图内存，低端机可能卡。
体积已经从 11MB 压到 4.24MB（分辨率不变），但像素量没变。

**可选方向**：把长图**切分成若干段**（例如每 4000px 一段），配合 `loading="lazy"`，
浏览器就只解码可视区域。需要改 `data.js` 的 `images` 结构 + `app.js` 渲染 + `optimize_calendar.py` 产出分片。

### 🟡 6.6 历史日期下的 header 状态区会"混搭"两个日期（**部分已修**）

已修：兜底的计划时间现在带 `(计划)` 标注（见 6.1~6.3 那张表最后一行），不会再被读成真实更新时间。

未修：`srcMeta(r)` 里早报/晚报时间取**当前展示的那一天**，但量价取 `screenerList()[0]`、
日历取 `calendar[0]` —— **永远是全局最新**。实测（周三白天，用户翻到 09-04 看历史）：

```
footer 实际渲染（旧版）：
   早报 08:33 · 晚报 21:05 · 量价选股 15:10 · 投资日历 09-06
   └─ 09-04 的 ────────────┘   └─ 09-10 / 09-06 的（与展示日期无关）
```

同一条状态栏里混了两个日期，而量价那行的 `15:10` 还是计划时间。

**未改的原因**：量价与日历**本来就不是按日期切分的**（它们各有自己的时间轴、且日期条在这两个 Tab 下会被隐藏）。
要改得先定产品语义 —— 是隐藏这两行，还是标注成「量价（最新 09-10）」。这个决定得你来做。

### ⚪ 6.7 `verify.gain` 的语义不是实盘收益

目前记的是「验证日收盘涨跌幅（相对昨收）」。而推荐股平均高开 3.78% ——
**按"开盘买入"的实际口径是亏的**，但页面显示 ✅+3.12% 会让人以为赚了。

**建议**：增补 `buyRet` / `openPct` / `locked`（一字板）字段，前端改显示实盘口径。
（`tools/verify.js` 里已有相关注释）

### ⚪ 6.8 数据源覆盖范围

行情只覆盖**沪深主板**（`fs=m:0+t:6,m:1+t:2`），创业板/科创板/北交所的推荐股：
- 量价选股：**主动排除**（设计如此）
- 次日验证：**永远验证不到**（推荐了也没有行情可标）

| `href` 未做协议白名单 | `c.url` / `links{}` 直接进 `href`（已做 HTML 转义，能防属性逃逸，但不防 `javascript:`）。数据源是自己控制的，风险低 |
| 缺 `apple-touch-icon` | iOS「添加到主屏幕」会用页面截图当图标，而不是 `icon.svg`。补一张 180×180 PNG 即可 |
| `updatedAt` 前端未使用 | 数据里写了，但页面没用它做任何判断（判断全靠 `generatedAt`） |
| 页面在后台时不轮询 | 回到前台会立刻查一次，行为正确；但如果手机浏览器把页面冻结，回来时也不会自动刷新 —— 需要手动点更新 |
