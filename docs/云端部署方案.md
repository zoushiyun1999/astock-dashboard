# A股推送系统 · 云端部署架构方案

> 版本 v1.0 ｜ 2026-09-10
> 目标：把「简报生成 → 定时调度 → 消息推送 → 网页托管」四件事全部搬上云，**并让访问链接永不失效**。

---

## 〇、先说结论：链接不稳定的根因不是 bug，是架构

现状链路：

```
本地 WorkBuddy automation（跑在你的 PC 上）
  → WebFetch 抓取 + AI 读图摘要
  → 写 dashboard/data.js
  → workbuddy_sites_deploy → e2b 动态沙箱 → 返回 shareLink
  → 微信里推送这个 shareLink
```

这条链路有 **三个结构性缺陷**，任何一个都会导致你今天的处境：

| # | 缺陷 | 后果 | 能否靠"修"解决 |
|---|---|---|---|
| 1 | **托管形态是动态沙箱** | 每次部署分配新沙箱、停旧沙箱；空闲自动停机（错误码 12809）；域名还从 `cloudstudio.club` 切到 `app.workbuddy.link` | ❌ 平台机制如此，永远会漂 |
| 2 | **链接在三个地方硬编码** | automation prompt、README、微信模板各写一份。域名一变，三处全成死链，已经积累了两代失效域名 | ✅ 可修 |
| 3 | **生成依赖本地 PC 开机** | 休眠/关机 → 整天数据缺失（9/8 全天早报+晚报为空），看门狗只补当天 | ✅ 可修 |

**核心结论：只要还用"每次部署生成新环境"的托管方式，链接就必然漂移。修修补补没用，必须换成「静态托管 + 固定域名」——URL 由你自己控制，与部署次数、托管商彻底解耦。**

---

## 一、目标架构

```
┌───────────────────────── 云端（永不关机）─────────────────────────┐
│                                                                   │
│  【调度层】GitHub Actions（cron / repository_dispatch）             │
│      00:30 UTC 早报 ｜ 06:30 UTC 选股 ｜ 13:00 UTC 晚报            │
│      13:30 UTC 验证 ｜ 每日 20:00 UTC 链接体检                      │
│                          │                                        │
│                          ▼                                        │
│  【生成层】Node 脚本 + LLM Adapter                                 │
│      抓取 → 结构化 →（可选）LLM 摘要/读图 → 代码校验 → 写 data.js   │
│                          │                                        │
│                          ▼                                        │
│  【存储层】Git 仓库（唯一事实源）                                   │
│      data.js 全量入库 + 每次 commit + 每日 snapshot artifact        │
│          │                                    │                   │
│          ▼                                    ▼                   │
│  【发布层】GitHub Pages                    【备份镜像】国内静态托管   │
│      （主站，免费/永久）                     （EdgeOne / Cloudflare） │
│          │                                                        │
│          ▼                                                        │
│  【推送层】Server酱 → 微信（链接从 SITE_URL 读取，绝不硬编码）        │
└───────────────────────────────────────────────────────────────────┘
                          │
                          ▼
              自有域名  asx.你的域名.com
                    （DNS CNAME）
                          │
                          ▼
                  📱 手机浏览器 / PWA
```

**设计原则（三条，决定了整个方案的形态）：**

1. **静态优先**：看板是纯静态文件（`index.html` + `data.js`），没有后端、没有运行时，因此**不存在"服务停机"这回事**，也几乎零成本。
2. **Git 是唯一事实源**：所有数据、配置、链接都进仓库。数据可回滚、可审计，且天然是发布触发器。
3. **链接与托管商解耦**：URL 由自有域名的 DNS 决定。哪天 GitHub Pages 不好用了，改一条 CNAME 指向镜像即可，URL 一个字都不变。

## 二、模块一：网页托管与访问（最关键）

### 2.1 链接永久性的三档分级

| 等级 | 形态 | 示例 | 稳定性 | 说明 |
|---|---|---|---|---|
| **L1 永久** ✅ | 自有域名 + DNS CNAME | `https://asx.xxx.com/` | **不丢失** | 换托管商只需改 DNS，URL 不变。**这是唯一满足"长期有效"的方案** |
| L2 持久 | 平台固定项目域名 | `xxx.pages.dev`、`xxx.edgeone.app` | 只要项目在就在 | 比沙箱稳得多，但绑死平台 |
| L3 漂移 ❌ | 动态沙箱 | `3000-<uuid>.e2b...` | 每次部署都变 | **当前状态，必须淘汰** |

> **一个诚实的补充**：免费二级域名（L2）其实已经比现在好非常多，可以先用着。但只要你想要"链接绝不丢失"，就只有一个答案——**自己持有一个域名**。一年成本约 ¥30–60，这是整个方案里性价比最高的一笔投入。

### 2.2 托管选型（A/B/C 排序）

**方案 A（推荐）：GitHub Pages 主站 + 国内镜像备站 + 自有域名**

- 主站：GitHub Pages —— 免费、无流量上限、Actions 原生集成（`actions/deploy-pages@v4`），你的 `.github/workflows/` 里已经写好了部署步骤。
- 备站：腾讯云 EdgeOne Pages（国内节点，有免费额度，给 `*.edgeone.app` 固定域名）或 Cloudflare Pages。
- 入口：自有域名 CNAME 指向主站；主站连续不可用 >30 分钟时，手动/自动把 CNAME 切到备站。
- 代价：GitHub Pages 在国内访问速度因运营商而异，偶有抖动。

**方案 B：纯国内托管（EdgeOne Pages / 阿里云 OSS+CDN）**

- 优点：国内访问最快最稳。
- 代价：用自有域名走国内 CDN **需要 ICP 备案**（数天到数周）；不用自有域名则只能用平台二级域名。数据回写与调度也要另想办法（对象存储 + 函数计算）。

**方案 C：维持现状（动态沙箱）** —— 直接否决，问题根源就在这里。

> 我的建议：**A 起步，域名到手后若要国内速度再叠加 B**（此时只需改 DNS，不返工）。

### 2.3 发布流程（覆盖式，不改 URL）

```yaml
# .github/workflows/publish.yml（节选核心）
- name: 上传 Pages 产物
  uses: actions/upload-pages-artifact@v3
  with:
    path: dashboard        # 只有 dashboard/ 作为站点根

- name: 部署到 GitHub Pages
  id: deploy
  uses: actions/deploy-pages@v4
```

关键：**发布是"覆盖同名站点"，不是"新建环境"**。这是 URL 能保持不变的技术前提——沙箱方案做不到这一点。

### 2.4 前端必须做的三处改造

1. **自定义域名文件**：`dashboard/CNAME`（内容仅一行：你的域名）。每次部署都会带上，防止 Pages 配置被重置后域名掉线。
2. **PWA 落地**：`dashboard/manifest.json` 已存在，补一张 192/512 图标 + `apple-touch-icon`，手机「添加到主屏幕」后图标固定，不再依赖收藏夹里的旧链接。再生成一张二维码 PNG 存进仓库，扫码即达。
3. **版本号防缓存**：保留 `tools/bump_version.sh`，但改为在 Actions 里执行（现在依赖本地执行，本地不跑就缓存不刷新）。

## 三、模块二：内容生成（云化难度最高，分阶段做）

### 3.1 现状盘点：哪些能直接上云

| 环节 | 依赖 | 能否纯云端 | 现状 |
|---|---|---|---|
| 量价选股 | 行情 API + 纯计算 | ✅ 完全可 | `tools/screener.js` 已可跑，workflow 已写好 |
| 次日验证 | 日K + 纯计算 | ✅ 完全可 | `tools/verify.js` 已可跑，workflow 已写好 |
| 个股代码校验 | 行情反查 | ✅ 完全可 | `tools/check_codes.js` |
| 数据体检 | 本地解析 | ✅ 完全可 | `tools/health_check.js` |
| 交易日历 | 静态 JSON | ✅ | `config/trade_holidays.json` |
| **早报/晚报摘要** | **LLM 语义理解** | ⚠️ 需 API | 现由 agent 的 WebFetch + 读图完成 |
| **晚报读图** | **多模态视觉** | ⚠️ 需 vision API | 淘股吧正文是图片，必须读图 |

**判断：选股/验证/校验这 60% 的工作量今天就能上云**（脚本现成，只是仓库还没 remote，从未真正跑过）。真正难的是 LLM 那 40%。

### 3.2 LLM 部分的云端化：Adapter 模式

不要为"本地 agent"和"云端 API"写两套逻辑。抽一层 `tools/llm.js`，两边共用同一份 prompt 与输出 schema：

```js
// tools/llm.js —— 统一 LLM 入口
// 优先级：OpenAI 兼容 API（云端）→ 环境变量缺失则抛出，由调用方降级
const ENDPOINT = process.env.LLM_BASE_URL;   // 如 https://api.deepseek.com/v1
const KEY      = process.env.LLM_API_KEY;    // 放 GitHub Secrets
const MODEL    = process.env.LLM_MODEL || 'deepseek-chat';
const VISION   = process.env.LLM_VISION_MODEL || '';  // 读图模型，如 glm-4v / qwen-vl

async function chat(messages, { json = true } = {}) { /* fetch 调用，json mode */ }
async function vision(imageUrls, prompt) { /* 图片 base64 + 提示词 */ }
module.exports = { chat, vision, available: () => !!(ENDPOINT && KEY) };
```

**降级链（必须内置，这是云端方案可靠性的保险丝）：**

```
LLM 可用 → 完整摘要（与现在质量一致）
   ↓ 失败/未配置
有原文文本 → 抽取式摘要（标题 + 前 N 条要点 + 原文链接）
   ↓ 失败
仅有标题 → 输出「标题 + 原文链接」卡片（已有类似降级逻辑）
   ↓ 全部失败
跳过 + 发一条「今日抓取失败」告警通知（绝不静默）
```

**诚实评估**：云端抓取韭研公社/淘股吧可能遇到反爬或 JS 渲染问题，需要实测。因此推荐 **混合生成模式**——

- **默认路径（云端）**：Actions 跑脚本抓取 + LLM 生成，全自动，PC 关机也不影响。
- **补写路径（本地）**：云端失败时，本地 agent 仍可按现有方式生成并 `git push`，一样触发发布。
- 两条路径写同一份 `data.js`、走同一套校验，互不冲突。

这样既解决了"PC 关机就没数据"，又不会因为云端抓取不顺利而让整个系统瘫痪。

### 3.3 数据写入约定（沿用，别改）

- `reports` 数组 **newest-at-bottom**，保留最近 7 天（`sort by date` 后 `slice(-7)`）。
- `calendar` 保留最近 5 篇；`screener` 是数组（最新在前）。
- 写回后**必须**跑 `tools/check_codes.js --fix --prune` 做名称↔代码双校验。
- 所有生成任务**幂等**：先检查今日是否已有数据，有则跳过或覆盖，不重复追加。

## 四、模块三：定时调度

### 4.1 时间表（注意 UTC 换算）

| 任务 | 北京时间 | cron（UTC） | 表达式 |
|---|---|---|---|
| 早报 | 08:30 | 00:30 | `30 0 * * 1-5` |
| 量价选股 | 14:30 | 06:30 | `30 6 * * 1-5` |
| 晚报 | 21:00 | 13:00 | `0 13 * * 1-5` |
| 次日验证 | 21:30 | 13:30 | `30 13 * * 1-5` |
| 链接体检 | 每日 04:00 | 20:00 | `0 20 * * *` |

容器内设 `TZ: Asia/Shanghai`，脚本里的时间判断才不会错位（交易日历判断依赖它）。

### 4.2 三个必须知道的坑

1. **cron 不保证准点**：GitHub Actions 高峰期可能延迟 15–60 分钟。早报 8:30 是要赶开盘的，延迟不可接受。
   → **解法**：关键任务改用外部定时器（cron-job.org / Cloudflare Workers Cron）准点打 `repository_dispatch`，Actions 只负责执行。或者把早报 cron 提前到 00:10 UTC 并容忍延迟。
2. **仓库 60 天无活动会禁用 schedule**：加一个 keepalive workflow，每周一次空 commit 保活（对长期运行的项目是刚需）。
3. **并发 push 冲突**：每个 workflow 加 `concurrency: group: <name>; cancel-in-progress: false`，你现有的两个 yml 已配置，新增的照抄。

### 4.3 Workflow 骨架（四个任务共用）

```yaml
name: 早报
on:
  schedule: [{ cron: '30 0 * * 1-5' }]
  repository_dispatch: { types: [morning] }   # 供外部定时器准点触发
  workflow_dispatch: {}

permissions: { contents: write, pages: write, id-token: write }
concurrency: { group: morning, cancel-in-progress: false }

env:
  TZ: Asia/Shanghai
  SITE_URL: ${{ vars.SITE_URL }}              # 唯一链接来源

jobs:
  morning:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }

      - name: 幂等检查（今日已有数据则跳过）
        id: guard
        run: node tools/should_run.js morning >> $GITHUB_OUTPUT

      - name: 生成
        if: steps.guard.outputs.run == '1'
        env: { LLM_API_KEY: ${{ secrets.LLM_API_KEY }} }
        run: node tools/morning.js

      - name: 校验 + 版本号
        if: steps.guard.outputs.run == '1'
        run: |
          node tools/check_codes.js --fix --prune
          bash tools/bump_version.sh

      - name: 提交
        if: steps.guard.outputs.run == '1'
        run: |
          git config user.name "github-actions[bot]"
          git config user.email "github-actions[bot]@users.noreply.github.com"
          git add -A && git commit -m "早报 $(date +%F) [skip ci]" || echo "无变化"
          git pull --rebase && git push

      - name: 发布
        if: steps.guard.outputs.run == '1'
        uses: actions/upload-pages-artifact@v3
        with: { path: dashboard }
      - if: steps.guard.outputs.run == '1'
        uses: actions/deploy-pages@v4

      - name: 微信推送
        if: steps.guard.outputs.run == '1'
        env: { SCT_KEY: ${{ secrets.SCT_KEY }}, SITE_URL: ${{ vars.SITE_URL }} }
        run: node tools/notify.js morning
```

> **`[skip ci]` 很重要**：数据 commit 不应再触发部署 workflow，否则会形成提交→部署→提交的死循环。

## 五、模块四：消息推送

- 通道不变：Server酱（`sctapi.ftqq.com`）→ 微信，国内可达。
- **Key 必须进 GitHub Secrets**：现在 Server酱 key 是明文写在早报 automation 的 prompt 里的，属于凭据泄露面。迁移时顺手**轮换一次 key**。
- 推送内容统一由 `tools/notify.js` 生成，链接**只从 `vars.SITE_URL` 读**：

```js
const SITE = process.env.SITE_URL;
if (!SITE) throw new Error('SITE_URL 未配置——这是防止硬编码链接的最后一道闸');
```

- 通知策略：早报/晚报/选股推送；验证不推送（与现网一致）；**失败也推送**（"今日抓取失败"告警，避免静默故障）。

## 六、模块五：链接长期有效 & 不丢失（重点）

这是你最关心的问题。答案分四层：**地址层、冗余层、数据层、监控层**。

### 6.1 地址层：让 URL 与一切解耦

```
自有域名  asx.xxx.com
   └── CNAME → GitHub Pages（主） / 国内镜像（备）
```

- **建立 `config/site.json` 作为单一事实源**：

```json
{
  "siteUrl": "https://asx.xxx.com/",
  "mirrorUrl": "https://xxx.edgeone.app/",
  "fallbackUrl": "https://<user>.github.io/<repo>/",
  "domainExpiry": "2027-09-10",
  "qrcode": "dashboard/qrcode.png"
}
```

- GitHub 仓库 variable `SITE_URL` 从该文件同步；**所有**推送脚本、README、页面页脚、二维码都从这里取。
- **硬拦截**：`tools/notify.js` 与体检脚本检查全仓是否出现写死的 `e2b.` / `sandbox` 域名，发现即报错。

> 这一条比任何技术手段都重要：你过去丢链接，不是因为域名会变，而是因为**同一个链接被抄在了三个地方、且没人负责更新**。

### 6.2 冗余层：三条独立可达路径

| 优先级 | 路径 | 失效条件 |
|---|---|---|
| 1 | 自有域名（DNS 指向主站） | 域名过期 / DNS 故障 |
| 2 | GitHub Pages 官方地址 `<user>.github.io/<repo>/` | 仓库被删 |
| 3 | 国内镜像固定域名 | 镜像项目被删 |

三条路径**互不依赖**：微信推送里主推 1，README 和仓库 About 里三条都写；页面底部放一个小号"备用入口"链接。任何一条挂了，用户仍有路可走。

### 6.3 数据层：数据不丢（不只是链接不丢）

- **Git 全量历史**：每次生成即 commit，`data.js` 168KB，一年也就几十 MB，git 完全扛得住。写坏了 `git revert` 秒回滚。
- **每日快照**：Actions 每日把 `data.js` 上传为 artifact（保留 90 天），作为仓库之外的第二份拷贝。
- **月度归档**：每月 1 日打一个 `snapshot-YYYY-MM` tag。
- **仓库镜像**：同时 push 到 Gitee（国内可clone，防 GitHub 不可达），一条 `git remote set-url --add` 即可双推。

### 6.4 监控层：故障早于用户发现

每日 20:00 UTC 跑 `tools/health_check.js`（云端版）：

1. **HTTP 探测**：请求 `SITE_URL`、`fallbackUrl`、`mirrorUrl`，校验返回 200 且 HTML 含 `A股速览` 关键字。
2. **新鲜度检查**：解析线上 `data.js` 的 `updatedAt`，超过 20 小时未更新 → 告警（能抓出"调度没跑"）。
3. **数据体检**：`reports` 条数、字段完整性、个股代码有效性。
4. **域名到期提醒**：距 `domainExpiry` < 30 天 / < 7 天 → 微信推送续费提醒（**域名过期是"链接丢失"最常见的真实死因**）。
5. 任一项失败 → Server酱推送「⚠️ 看板健康检查失败：xxx」，并自动在 Issues 开一条记录。

### 6.5 防链接丢失清单（落到人身上）

- [ ] 域名开启**自动续费**，并在日历设次年到期提醒
- [ ] 域名注册邮箱保持可用（找回域名的唯一凭证）
- [ ] 仓库开启 **branch protection**，禁止 force push 误删历史
- [ ] 手机「添加到主屏幕」+ 打印一张二维码贴在显示器上（物理固化）
- [ ] GitHub / 域名注册商账号开启 2FA

## 七、完整数据流转时序（以早报为例）

```
00:30 UTC（08:30 CST）
  │
  ├─1─ Actions 触发 / 外部定时器 repository_dispatch
  │
  ├─2─ tools/should_run.js：今天是交易日？今日已有 morning？→ 否，继续
  │
  ├─3─ tools/morning.js
  │      ├─ fetch 韭研公社主页 → 解析最新帖标题/日期/链接
  │      ├─ 非今日发布 → 写日志、优雅退出（不发空消息）
  │      ├─ 抓正文 → LLM 提炼 5 个板块 + 今日关注
  │      └─ 合并进 data.js（保留 evening/calendar，滚动 7 天）
  │
  ├─4─ tools/check_codes.js --fix --prune（名称↔代码双校验）
  │
  ├─5─ tools/bump_version.sh（刷新 v= 参数防缓存）
  │
  ├─6─ git commit（[skip ci]）+ push（主仓 + Gitee 镜像）
  │
```

## 十、已落地的实现（2026-09-10 更新）

Phase 1 的前端与配置部分已完成，以下文件已存在于仓库，可直接用：

### 10.1 无感自动刷新（已实现并通过本地截图验证）

三级协同，既省流量又不用手动刷新：

| 文件 | 作用 |
|---|---|
| `tools/export_json.js` | 从 `data.js` 派生 `data.json`（全量）+ `version.json`（仅几百字节，含内容 md5 key） |
| `dashboard/data.json` | 前端 fetch 用的全量数据（已改为 JSON 格式，不再解析 JS 正则） |
| `dashboard/version.json` | 版本探针，前端每分钟只拉这个 |
| `dashboard/js/app.js` | 轮询逻辑改造：探测 version → key 变了才拉全量 → **就地重渲染** |

关键改进（相对原实现）：

- 原来每分钟拉 **168KB** 的 `data.js` 并用正则匹配 `updatedAt`；现在每分钟只拉 **~200B** 的 `version.json`，变更时才拉全量。
- 原来发现新数据只能「整页 reload」，会丢失 Tab 和滚动位置；现在 `applyUpdate()` 就地替换数据后重渲染，**Tab、滚动位置、浏览的日期全部保留**（已用 Edge 无头截图验证：切到「量价」Tab 触发更新后仍停在量价）。
- 页面切到后台（`document.hidden`）暂停轮询，回到前台立刻查一次，手机端省电。
- **本地 `file://` 打开时自动跳过轮询**，数据源仍是 `index.html` 引入的 `data.js`，不会因 CORS 白屏。
- `window.__aStockDebug` 暴露 `applyUpdate` / `showUpdateBar`，方便调试。

> 发布链路不需要额外配置：`bump_version.sh` 已串联 `export_json.js`，定时任务跑 bump 就会同步产物；
> CI 里 `publish.yml` 也会重新导出一次，确保两端一致。

### 10.3 待你在 GitHub 上完成的操作（无法由脚本代劳）

1. **建仓库并 push**（当前本地仓库没有 remote，这是所有云端化的前置条件）。
2. **Settings → Pages**：Source 选 `GitHub Actions`。
3. **Settings → Secrets and variables → Actions**：
   - Secret：`SCT_KEY` = 你的 Server酱 key（**建议先轮换一次**，旧 key 曾明文出现在 prompt 里）
   - Variables：`SITE_URL` / `FALLBACK_URL` / `MIRROR_URL` / `DOMAIN_EXPIRY`（值同 `config/site.json`）
4. **自定义域名**：把 `dashboard/CNAME` 内容改成你的域名，并在域名 DNS 处按 Pages 提示添加解析记录。
5. 手机打开站点 → 「添加到主屏幕」。
