# 自动化替代方案 · 不依赖 WorkBuddy 定时任务

> 问题：如果不用 WorkBuddy 的定时任务，有没有别的办法自动抓信息源、更新网页？
> 结论先行：**有，而且大部分环节现在就能脱钩。真正需要大模型的只有一个环节，而那个环节有替代品。**

---

## 0. 先把问题拆对：哪些环节真的需要"agent"？

整个系统里，**只有「读图 + 提炼」这一环需要理解能力**，其余全是普通程序就能干的活。

| 环节 | 是否依赖大模型 | 现状 |
|---|---|---|
| 抓正文 / 下载图片 | ❌ 纯 HTTP | 已可脚本化 |
| 行情取数（东财/新浪/腾讯） | ❌ 纯 HTTP | 已在 `tools/screener.js`、`verify.js` 里跑 |
| 条件筛选、次日验证 | ❌ 纯计算 | 已是零依赖脚本 |
| 写入 data.js、版本号、导出 JSON | ❌ 纯文件操作 | 已在 `bump_version.sh` 里跑 |
| 发布到固定域名 | ❌ 纯静态搬运 | GitHub Pages，与调度器无关 |
| **读图（湖南人连板梯队表）** | ✅ **需要** | 目前由 agent 承担 |
| **把长文提炼成结构化 JSON** | ✅ 需要 | 目前由 agent 承担 |

**如果只替换调度器、保留大模型**，就是纯工程问题，几天能做完。
**如果想连大模型一起去掉**，就要接受内容形态变化——见 §3。

## 1. 一个改变结论的实测发现

我解析了 `tmp_hunanren_0910.html`（湖南人 9/10 帖子，172KB，47 张图），发现：

**湖南人的帖子不是"纯图片"，而是文字 + 图片混排。**

主帖正文的**完整文字内容**就在帖子 HTML 的 `subject` 属性里，包含：

- 一、复盘、龙虎榜（指数、成交额、活跃板块、机构动向）
- 二、热点题材（玻纤 / 大金融 / 覆铜板 / 算电协同…**每个都带消息面全文**）
- 三、盘前消息（公司公告 11 条 + 重要新闻）
- 四、外围市场情况及盘前思考题

图片只是其中的**连板梯队表**等结构化表格。

**这意味着：不用任何大模型，脚本直接抓文字，就能拿到晚报 70–80% 的内容。** 唯一损失的是连板梯队表。

> 另外发现：评论区（`plContent` / `plItem`）里常有用户贴的完整文字版复盘，可作为交叉验证源。

## 2. 五条路线

### A. GitHub Actions 定时触发 ★ 推荐起点

**做法**：把生成脚本推上云，用 workflow 的 `schedule` 触发。

- ✅ **完全不需要你的电脑开机**，这是它相对现状最大的价值
- ✅ Public 仓库计算分钟数**无限免费**
- ✅ 已有基础：`publish.yml` / `health.yml` / `keepalive.yml` 已经在跑
- ⚠️ cron 最小间隔 5 分钟，实际**延迟 15–30 分钟**（整点最堵）
- ⚠️ Public 仓库 60 天无活动会**自动停用** schedule（已有 `keepalive.yml` 兜底）
- ⚠️ 从海外 runner 访问东财 / 新浪**必须带 Referer**（已实测确认）

**适用任务**：选股（14:30）、验证（21:30）——这些对时间精度要求不高，晚 20 分钟无所谓。

**不适用**：早报（8:10 发布，8:30 要推，延迟 30 分钟就废了）。

> 代价：需要把"agent 生成"改写成"调 LLM API"。这不是搬迁，是**重写**。

---

### B. 本机 Windows 计划任务 + 自己的脚本 ★最强，但有致命约束

**做法**：用 Windows 任务计划程序直接跑 `node tools/xxx.js`，完全不经过 WorkBuddy。

- ✅ **最可控**：时间精确到分钟，无延迟
- ✅ 可以调本地大模型（Ollama），**零 API 成本、数据不出本机**
- ✅ 脚本都已就绪，改造成本最低
- ❌ **仍然要求电脑开机** —— 如果你的核心痛点是"关机就断更"，这条路**没解决任何问题**
- ❌ **实测坑：`schtasks.exe` 被本机安全策略拦截**（Program Blacklist）。需要用图形界面「任务计划程序」手动创建，或在安全中心里放开

**判断**：如果你的电脑本来就是 7×24 开机（或愿意设置永不睡眠），这是性价比最高的方案；否则直接排除。

---

### C. 现成监控服务（changedetection.io / RSSHub）

**做法**：不改代码，用开源工具监控页面变化。

**RSSHub 路由已覆盖你的源**（实测查证）：
- 淘股吧博客 → `/taoguba/blog/:id`（湖南人 = 444409，行鱼 = 563404）
- 韭研公社 → `/jiuyangongshe/user/:uid`、`/jiuyangongshe/latest`

**changedetection.io**：自托管网页变更监控，支持 CSS/XPath 选择器、视觉 diff、80+ 通知渠道，可对接 webhook。

- ✅ 零代码，部署即用
- ✅ 能精确监控"湖南人博客有没有新帖"
- ⚠️ **自托管同样需要一台 24 小时开机的机器或 VPS** —— 又回到原点
- ⚠️ **本机实测：公共 `rsshub.app` 不通**（直连超时、代理 502），和 `github.com` 同样的原因。要用只能自建 RSSHub 实例
- ⚠️ 只能**告诉你"更新了"**，不能把内容提炼成结构化 JSON

**最佳用法：当作"探针层"**——它负责高频检测"源更新了没"，检测到变化才触发后面的生成。这正是 `docs/定时任务云端化方案.md` 里「探针/生成分离」的思路。

---

### D. 托管平台定时（Vercel Cron / 腾讯云函数 / 阿里云 FC）

**做法**：把脚本部署为 serverless 函数，用平台自带的定时器。

- ✅ 不需要电脑开机，国内节点需备案
- ✅ 云函数支持秒级定时
- ⚠️ 改造量最大：要处理依赖打包、环境变量、日志
- ⚠️ 平台绑定，换平台要重做

**判断**：只在 A 的时间精度不够时才考虑。目前你的任务没有这个需求。

---

### E. 放弃"理解"，只做"变更检测" ★今天就能上线

**做法**：不提炼、不总结。脚本定时检测源页面/API 有没有变，变了就把**原始内容**写进看板并推送。

- ✅ **零大模型依赖**，`tools/screener.js` 这类纯脚本改都不用改
- ✅ 完全自动化，断网/关机之外没有失败点
- ❌ 看板内容形态会退化：从"精炼的结构化总结"变成"原文搬运"

**折中版本**：用**规则 + 正则**做半结构化提取。湖南人正文已经有清晰的 `一、复盘` / `二、热点题材` / `三、盘前消息` 标题结构，用正则切段是完全可行的——**不完美，但零成本、零依赖、今天就能跑**。

## 3. 关键分水岭：大模型这一环怎么处理

这是整个决策的核心。三条路：

| 方案 | 成本 | 质量 | 改造量 | 说明 |
|---|---|---|---|---|
| **① 调用国内 LLM API** | ¥6–10/月 | 接近现状 | 中 | 百炼/智谱/DeepSeek，实测从云端 runner 全部可达（返回 401 仅缺 Key） |
| **② 本机 Ollama + 开源模型** | ¥0 | 中等偏下 | 中 | 需 8GB+ 显存；**只能搭配路线 B**，因为模型在本机 |
| **③ 不要大模型，用规则提取** | ¥0 | 明显下降 | 小 | 见 §2-E，配合已发现的文字正文结构 |
| **④ 保留 agent 只做"读图"** | 现状 | 不变 | 最小 | 脚本干脏活，读图时才唤起我——但这就还依赖 WorkBuddy |

**我的判断**：
- 如果要**保持现在的输出质量**，① 是唯一可接受的答案，且成本极低（每月不到一杯咖啡）。
- 如果只想**解决"关机就断更"**，并且能接受内容稍粗，③ 性价比最高。
- ④ 是伪解——它把"依赖"从调度层挪到了内容层，没真正解绑。

## 5. 推荐路径

### 如果只想"不被 WorkBuddy 绑定"（推荐先做这个）

**最小改动解绑**：把**今天就已经是纯脚本**的部分搬出去，完全不碰大模型。

```
现在就能搬走、零改造成本：
  · 量价选股（tools/screener.js）   → GitHub Actions / 计划任务
  · 次日验证（tools/verify.js）     → 同上
  · 数据发布（tools/publish.sh）    → 本来就跑在 GitHub Actions 上

需要重写才能搬走：
  · 早报生成 / 晚报生成（依赖 agent 的读图与提炼）
```

**搬走这三个之后，系统里就只剩早报/晚报两个环节依赖我。** 而这两个环节**天然可以人工兜底**——真断更了，你发一句话我就补上，成本极低。

### 如果追求彻底无人值守

按 `docs/定时任务云端化方案.md` 的四阶段走，但**先做一件事**：
用 2 周时间，在本地建一个**新脚本**（不走 WorkBuddy）并行生成早报/晚报，和现有输出逐条对比。**质量过关再切换，不过关就停掉，损失为零。**

不要一上来就切换——现有系统的"智能"寄生在 agent 上，直接替换把质量替换掉是最大的风险。

## 6. 我建议的第一步

**不要先动调度器。先花半天验证一个假设**：用规则提取湖南人正文，能做出多接近现在的晚报？

我可以写一个 `tools/fetch_hunanren_text.js`：
1. 抓博客页 → 定位主帖
2. 从 `subject` 属性解出正文 HTML
3. 按 `一、` `二、` `三、` `四、` 标题切段
4. 输出 JSON

跑一遍，看看不借助大模型能拿到什么。**这个验证有确定的答案，且不破坏任何现有东西。** 验证完再决定要不要投入云化改造。

## 7. 一句话总结

- **"更新网页"这一环早已和调度器解耦**——只要数据文件变了并提交，GitHub Pages 自动发布。
- **系统的骨架（数据源 → 筛选/验证 → 发布）现在就能脱离 WorkBuddy**，因为它们是零依赖脚本。
- **只有早报/晚报的"读图+提炼"依赖我**，而湖南人正文其实是文字混排，这一依赖比想象中小得多。
- **真正的瓶颈从来不是"用谁的定时任务"，而是"生成内容需要理解能力"**。解决它只有两条路：花钱买 API（¥6–10/月），或者降低内容形态的期待。
- **别急着推倒重来。** 先做 §6 那个半天能完成的验证，它会告诉你哪条路值得走。
