结论先行

你的三个核心需求里，有两个半已经有现成能力，不需要开发。选股、热点板块、个股跟踪所需的行情/财务/资金流/板块/条件筛选数据，已被本机已连接的腾讯自选股与通达信能力完整覆盖；实测选股引擎是一个 3.1MB 的单文件 Node CLI，无需安装依赖，后端直接调用即可。

因此真正的开发量集中在三块：博主内容采集（最大不确定性）、LLM 摘要、前端展示。整体规模比"从零做一个股票网站"小一个数量级。

推荐路线：方案 A（本机单体）为基线 —— 产出 24–38 小时 AI 辅助工时，首年现金支出接近 ¥0，月度运行成本 ¥6–30，年维护 10–26 小时。若不想碰服务器运维，用 方案 C（低代码流水线）+ 轻量前端 可在 11–16 小时内出可用成果，代价是前端表现力和长期可扩展性下降。

最该警惕的不是技术选型，而是采集。公众号类内容没有官方接口，抓取在技术脆弱性和合规上都存在问题。建议把"手动投喂 / RSS"作为采集的默认路径，网页抓取作为增强项 —— 这个决策对总成本的影响，比选 A 还是选 B 大得多。

部署与维护

部署成本

  • 跑在现有 PC：¥0（仅电费，约 ¥30–80/年）
  • 远程访问：Tailscale 个人版免费（异地组网，无需公网 IP、无需备案）

维护成本

  • 依赖与系统升级：每月约 0.3–0.5h
  • 数据源接口变更：每年 1–3 次

  • 合计：10–26 h/年

方案 A 的两个真实弱点，要提前接受

  1. 机器不开就不跑。如果你希望"盘中随时提醒"，本机关机就断了。折中做法：把采集与选股的主任务留在本机（低频、跑批），只把"结果推送"交给一个更省电的常驻设备或手机端。
  2. Windows 上做定时任务的坑。优先用"计划任务 + 用户已登录时运行"，而不是把服务装成系统服务 —— 前者能复用你的用户环境（浏览器缓存、登录态），后者不行。涉及登录态的采集，必须在已登录会话下运行。

相比方案 A 多出来的是什么

  • 工时 +4 到 +9 小时：跨域、鉴权、环境分离、部署脚本、日志收集
  • 现金支出：从 ¥0 变成每年 ¥40–450

换回来的是什么

  • 7×24 在线，不依赖家里机器
  • 多设备访问（手机、平板）
  • 可为后续对外分享留接口

必须提前知道的三个约束

  1. 国内服务器 + 域名需要 ICP 备案，个人主体可以备案，流程通常 1–3 周。不备案也能用（直接用 IP 访问，或走云厂商提供的免备案测试域名），但体验和安全性都差。
  2. 低价促销机型的续费价会跳。¥38/年的秒杀机次年可能按 ¥35–45/月续。选购时优先挑"续费同价"档位，虽然首年贵几十块。
  3. 云服务器抓取国内财经站，IP 更"干净"，通常比家用 IP 更容易通过风控 —— 这是方案 B 在采集上反而是优势的一点，容易被忽略。

五、方案 C · 低代码流水线 最快见效

用 n8n（自托管 Docker）或 Dify / Coze 把"定时抓取 → LLM 摘要 → 落库 → 推送"串成可视化流程，前端直接复用第三方看板（飞书多维表格、Notion、Metabase）。选股部分直接调用已有 CLI 或对话式触发。

项内容
工时11–16 h：流程搭建 4–6h、LLM 节点与提示词调优 2–3h、看板配置 2–3h、选股对接 1–2h、调试 2h
部署成本n8n 自托管可跑在方案 A 的机器上 → ¥0；或云版 / Coze 免费额度 → ¥0；若单独开服务器 ¥38–99/年
月度运行LLM ¥6–30（同方案 A）；平台订阅 ¥0–50
维护工时6–15 h/年，比自建低，因为基础设施由平台承担

方案 C 的隐性代价

  • 数据沉淀在别人家。内容与摘要在第三方表里，导出能力受限，平台改版或涨价时迁移成本高。
  • 加站点会膨胀。每个站点一条流程，"逐步扩展"这个需求在低代码里反而比写适配器更痛 —— 这与你"后续可逐步扩展"的目标是冲突的。
  • 前端表现力弱。K线、板块热力图这类金融可视化在看板工具里做不出来。

判断：适合做"验证需求"的第一步，不适合作为终态。可以用它先跑通两周，确认你真正高频看的是哪几个视图，再决定自建时把力气花在哪。

六、方案 D · 纯前端 + 定时构建静态数据 不建议作为主线

先把话说直白："纯前端"在你的三个核心需求上都不成立。

需求纯前端为什么不行
采集博主内容浏览器同源策略会挡掉绝大多数目标站，除非对方明确开了 CORS。少数带开放 CORS 的接口可以，但覆盖面极小
LLM 摘要要么把 API Key 写进静态站点（链接一旦外泄即等于 Key 外泄），要么根本没有可调用的运行时
自动选股行情数据同样跨不过同源限制；即使能取，定时任务也无处运行

唯一自洽的形态，是把后端替换成 CI 的定时构建：GitHub Actions 定时跑采集与摘要脚本，产出 JSON 提交回仓库，前端只读静态文件。这不是"没有后端"，而是后端被托管了。

项内容
工时19–31 h（比方案 A 少在部署，多在与 CI 环境搏斗）
现金成本¥0（Pages 托管免费）
维护8–20 h/年

四个会让方案 D 实际落空的硬约束

  1. 配额很紧。私有仓库每月 2,000 分钟免费额度（公开仓库无限，但你的采集内容与代码会公开，通常不可接受）。若每天跑 24 次、每次 2 分钟，就是 1,440 分钟，几乎贴顶，失败重试就超。实际得压到每天 6–10 次。
  2. CI 运行器在海外。抓取国内财经站极可能被地区风控拒绝或返回空数据，这是最致命的一条。
  3. 无法交互查询。看不了"随便查一只股票"，只能看预设好的离线产物。个股跟踪这类需求基本废掉。
  4. 状态与检索能力弱。历史数据靠 git 提交历史，做"某博主观点随时间的变化"这类分析很别扭。

配额与价格数据来源：GitHub 官方计费文档（2026 年 9 月）。

八、真正的难点：博主内容采集

这一节的结论会影响你整个项目的成败，比选 A 还是 B 重要得多。请先确认目标站点清单 —— 不同站点的采集难度差 10 倍以上，报价也因此差一个量级。

难度站点特征技术路径与成本
低 提供 RSS/Atom 或公开 API（部分财经媒体、个人博客、雪球专栏的 RSS 镜像） httpx 直接拉取 + 解析。每站 1–1.5h（首次），之后基本不失效
中 网页有公开 JSON 接口但带基础风控（雪球、东方财富部分接口） httpx + 会话保持 + 限频（建议间隔 ≥ 30 分钟）+ UA 伪装。每站 2–3h，每年需修 1–3 次
高 微信公众号、需登录/App 端加密接口的内容 无官方接口。抓取违反其服务条款，技术上是脆弱的模拟客户端方案，且存在账号风险。每站 4–8h，且可能每周都要修。不建议作为主路径

对"高难度"站点的三条替代路径（按推荐度排序）

  1. 手动投喂 / 收藏夹（推荐默认路径）。做一个"粘贴链接或全文即可入库"的入口，配合浏览器书签脚本一键提交。成本 2–3h，永不失效，且天然规避了合规问题。缺点是需要你动手，但个人自用场景下，每天点几下并不算负担。
  2. 用付费 RSS 服务做中间层。市面上有把公众号转为 RSS 的第三方服务（多为按量付费，每月几元到几十元）。把不稳定的抓取外包出去，自己只对接标准 RSS。成本：每月 ¥10–50，开发 1h。这是"花钱买稳定性"的划算交易。
  3. 自建模拟客户端。只有当你确认必须全自动、且愿意承担长期维护时才做。务必限频、且明确仅个人研究使用，不外传原文。

合规边界（建议写进项目约束）

  • 仅采集公开可访问的内容，不绕过付费墙、不破解登录
  • 采集频率限定在低频（建议 ≥ 30 分钟一次），不对目标站造成压力
  • 只在本地留存原文，不对外二次分发；摘要是你自己的分析，不公开原文
  • 不基于本系统对外提供任何形式的荐股或投顾服务

十二、服务器配置评估：阿里云轻量 2核2G

结论：够用，而且有余量。真正的风险只有一个 —— 是否把无头浏览器放在服务器上跑。

先把负载画像想清楚

这个系统的负载特征很极端：单用户、低频、几乎全是 IO 等待。LLM 摘要是在等外部 API 返回，采集是在等目标网站响应 —— 这两件事占用 CPU 的时间接近于零。它跟典型网页应用的负载不是一回事，不能套用常规建站配置经验。

资源常态占用估算判断
CPU 2 核几乎闲置（<5%）严重过剩。IO 密集负载对核数不敏感，1 核也够
内存 2 GB系统 200–400 MB；FastAPI + uvicorn 80–120 MB；定时任务进程 50–100 MB；SQLite 数十 MB。合计约 400–600 MB用掉不到三分之一，宽松
磁盘 40 GB纯文本内容与摘要，每年几百 MB充裕
流量 / 带宽个人访问 + 采集请求，量级极小轻量套餐的流量包足够

唯一能把 2 GB 吃爆的东西

无头浏览器（Playwright / Puppeteer）。单个 headless Chromium 实例常驻 150–400 MB，每多开一个页面上下文可能再翻一倍。若需要渲染采集的站点有 3–5 个且并发抓取，2 GB 会触发 OOM Killer 杀进程，表现为「任务莫名其妙中断」。

对策（按推荐顺序）：

  1. 采集串行化 —— 一次只处理一个站点，绝不并发。个人场景下这个约束基本无感
  2. 加 2 GB swap —— 轻量服务器默认常常没有 swap，需手动创建。它不提升性能，但能把「进程被杀」变成「变慢」，是重要的安全垫
  3. 把渲染类采集挪回本机 —— 服务器只跑 httpx 这类轻量采集，渲染任务在本机跑完同步上去
  4. 升配到 4 GB —— 阿里云轻量支持升配，年付约 ¥350–500。遇到瓶颈再升，不必现在多花钱

三个要提前处理的实操问题

问题说明与做法
续费价会跳 ¥68/年是促销首年价，阿里云轻量 2核2G 的标准续费价约 ¥35–45/月（¥420–540/年），是首年的 6–8 倍。首年不受影响，但第二年这笔账要提前知道。后续续费时优先找「续费同价」档位（如阿里云 ECS 经济型 e 的 99 计划，¥99/年、续费不涨价）

别装带面板的镜像 宝塔一类的面板常驻 200–400 MB 内存，在只有 2 GB 的机器上是纯浪费。直接选 Ubuntu 22.04/24.04 或 Alibaba Cloud Linux 纯净镜像

推荐的系统配置

  • uvicorn 单 worker —— 不要按核数开多 worker。2 核开 4 个只会互相争内存，而你的负载根本不需要并发处理能力
  • SQLite 开 WAL 模式 —— 允许读写并发，避免采集写入时阻塞前端查询
  • 用 systemd 管理进程 —— 不要用 nohup，systemd 提供崩溃自动重启与开机自启
  • 配日志轮转 —— 定时任务日志不加限制会持续增长，是个人项目里最常见的「磁盘莫名满了」原因
  • 开 2 GB swap —— 见上文，重要的安全垫

不要在这台机器上同时跑 n8n

n8n 是 Node 常驻应用，仅自身就要 300–500 MB，叠加无头浏览器基本必然 OOM。2核2G 上「自建后端」与「n8n」二选一。

实测补充：两个影响架构的事实

1. 选股 CLI 无凭证依赖，可以直接部署到这台服务器。在清空所有环境变量的条件下（env -i）运行，它不需要任何本地配置或 token 文件，filter 子命令直接返回了真实行情数据。这意味着服务器能独立完成选股，不必依赖本机的开发环境 —— 方案 B 的架构成立。

2. 但数据服务本身会抖动。2026-09-11 21:10 实测：filter --preset LowPE 正常返回，而同一时刻 strategy macd_golden 与 label risk_st 都返回 service error。这是对方服务端的问题，不是配置问题。

第 2 点直接印证了前文的设计要求：选股结果必须落库留档。不要假设每天都能取到数，也不要假设失败后重跑即可恢复 —— 每天跑完把结果写进本地库，前端优先读本地；取数失败时降级展示上一次存档并明确标注日期。这是「数据源由第三方维护」这个便利性背后的必然代价。

十四、本地部署 · 无后台方案已实现并验证

「不需要后台」在本地是完全成立的，而且比云部署更简单。理由要回到第一性原理：后台服务存在的唯一理由是「随时响应请求」。而这个场景的数据一天只更新一次 —— 你根本不需要这个能力。

核心转变：把「在线服务」换成「离线批处理 + 静态文件」。没有常驻进程、没有端口占用、没有数据库服务、没有网络暴露。定时任务跑一个脚本，脚本拉完数据写文件就退出；前端是一个纯静态 HTML，双击就能打开。

关键技术点：数据为什么写成 data.js 而不是 data.json

浏览器在 file:// 协议下用 fetch('data.json') 会被同源策略拦截（本地文件被视为 opaque origin，读不到同目录文件）。而 <script src="data.js"> 属于经典脚本加载，不受同源限制。

所以数据以 window.DATA = {…} 的形式写出。这是「双击 HTML 就能看」能成立的前提 —— 不理解这一点，就会误以为纯静态方案必须起一个本地 http server。

两个新约束收窄了方案空间，其中一条也推翻了我此前的一个判断。本节记录收敛过程与实测数据。

约束

  • 域名未备案（自有域名已注册，但未走 ICP）
  • 没有 7×24 常开的设备 —— 电脑可以常开，但会关机；也无 NAS / 旧电脑 / 树莓派

澄清：未备案 ≠ 一定慢

关键在于用谁的域名。备案义务由「域名解析指向中国内地服务器」触发 —— 用自己的域名就触发，用平台分配的域名则不触发（义务在平台）。

用谁的域名备案实测/估算速度
自有域名（已注册未备案）只能走境外节点估算 670–1400ms
平台分配的 *.edgeone.cool 子域名无需备案实测首字节 0.32–0.50s

所以此前把「未备案」直接等同于「只能慢」是不准确的。代价只是地址不好记 —— 手机上「添加到主屏幕」即可解决，几十秒的事。

推翻：云函数并不省钱

原本设想「取数搬到云函数」来去掉"本机需开机"，前提是云函数免费。核实后该前提不成立：

项实际情况
腾讯云 SCF 免费额度已取消。前三个月免费试用，三个月后每月自动扣 ¥12.8（¥153.6/年）
免除条件仅当上个自然月的调用量、资源用量、外网流量均为 0
对比轻量服务器同价续费档 ¥99/年 —— 比云函数还便宜

结论：拿云函数替代服务器来省钱是伪命题。网上「云函数每月 100 万次免费」的说法已是过时信息。

落地方案：开机补跑 + 当日幂等

既然取数只需每天一次，「某一天没跑」和「从没跑过」就是同一件事 —— 补跑即可覆盖，不需要一台常驻设备。

情况结果
18:10 时电脑开着正常更新
18:10 时电脑关着下次开机后自动补跑
今天已更新过又触发立即退出，不重复打第三方接口
当天全部取数失败不锁死，允许后续重试（判据是成功数 > 0）

一个容易踩的实现陷阱：Windows 计划任务的命令行没有「错过计划时间后补跑」这个开关 —— 对应设置 StartWhenAvailable 只存在于 XML 定义和 PowerShell 两种途径。用 schtasks /Create 的参数是配不出来的，会静默丢掉这个行为。所以本项目用 mkschedule.py 生成 XML（必须 UTF-16 编码，schtasks 拒收 UTF-8）再导入。

唯一残留的取舍：电脑长期关机期间，页面显示的是最近一次成功取数的数据（页面顶部标注实际数据时间）。要彻底消除这一点，需把取数搬到云端，但目前没有既免费又验证过的路径 —— 云函数要收费，最低配服务器要 ¥99/年。

成本估算口径说明：云服务器与 LLM 价格为 2026 年 9 月公开信息（含促销价，续费价会变动）；工时按 AI 辅助开发估算，实际会因目标站点反爬强度和你的调试习惯浮动 30% 左右；外包参考价 —— 此类个人小工具通常按打包价谈，市场区间大致 ¥5,000–25,000，主要取决于采集站点的难度。
